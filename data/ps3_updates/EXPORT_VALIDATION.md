# PS3 update export validation

This is historical validation of the curated export snapshot. Repository status
reviewed 2026-10-06: the data repository is now `d1reimagined-data`; files were not
regenerated by that rename. Runtime checks in the source project have advanced
since this export. Statements below about untested client behavior describe the
original export scope, not current whole-project status. See the
[data README](../README.md) and
[source handoff](https://github.com/p3n1cillin/d1reimagined/blob/master/notes/HANDOFF-2026-10-06.md).

Regenerated on 2026-09-28 from the decrypted BLES01857 EBOOTs with
`p3n1cillin/d1xenia` commit `c0ccd88257c40ef26f04d771dd3cbc1587208f02`
(`scripts/d1_types.py` and `scripts/d1_builddiff.py`). The earlier exports used
the 01.00 type-definition layout for later executables, found only 352/351
types in 01.13/01.24, and falsely reported thousands of removed types.

| Build | Decrypted ELF bytes | SHA-256 | Types recognized |
| --- | ---: | --- | ---: |
| 01.00 | 24,853,536 | `e14e1cedaf85a10ef08a3d4b86d86ff942f222cd27fde9a68d612947169846c6` | 4,387 |
| 01.13 | 25,901,408 | `c0db242499726d46fc9213436a7ff8df03fba9d89e7a85e170799081c663b122` | 4,942 |
| 01.24 | 26,181,096 | `e7f100b38bbaf6c23f71b390fdb103d31b427187c38dcfbd47e09c94c4a44206` | 5,041 |

The corrected scanner detects the later definition layout: the field-list
pointer is at definition +0x34, and each field entry starts with a repeat
count. Fixed arrays are expanded back into individual fields for comparison.
Re-exporting 01.00 produced a byte-identical `types_01.00.json` (SHA-256
`1b677ba5073fa320e2973dc89f93bcddc6f17035e6f516e676eb609fa86c39a2`).

The corrected reports now find:

| Comparison | Matched | Structurally identical | Changed | Removed | Added |
| --- | ---: | ---: | ---: | ---: | ---: |
| 01.00 → 01.13 | 4,317 | 3,766 | 551 | 70 | 625 |
| 01.00 → 01.24 | 4,308 | 3,744 | 564 | 79 | 733 |
| 01.13 → 01.24 | 4,917 | 4,858 | 59 | 25 | 124 |

The matcher now reserves unchanged handles first and uses each new handle at
most once. Counts balance against the old and new export sizes. Matches with
changed handles remain heuristic: equal or similar structure alone cannot
prove two types have the same runtime purpose.

These are **static export comparisons**. They have not been checked against
type exports from a running 01.13 or 01.24 client. The type JSON files contain
no package service table; the separate `services_01.24.json` supplies that map.
The service-table analysis is in `d1xenia/notes/final-build.md`.

Validation on the current code branch: 59 server tests ran successfully (one skipped),
and 21 script tests passed. The tests use synthetic fixtures and do not prove
complete runtime type coverage.

Mission-state preflight on 2026-09-28 with `d1xenia` commit
`34f34a6aa0f1c4b0b7d52a4c78c2c122b14edce1`:
`scripts/d1_mission_preflight.py`
encoded and decoded all 80 scripted state changes in `a_guardian_rises.json`
and `tower_npcs.json` against both the saved 01.00 activity schema and this
directory's corrected `types_01.24.json`; both passed. The 01.24 squad state
`0x8080071e` grew from 0x60 to 0x7c bytes. Its 2-bit, bias-1
existing-member field moved from +0x5c to +0x74. The former scripts named
+0x5c in 56 squad changes, which the 01.24 encoder silently omitted. The
code branch now resolves `squad_existing_members` to the offset for the
selected schema and rejects dropped fields before a run. Client behavior on
01.24 remains untested.

Core build preflight on 2026-09-28 with `d1xenia` commit
`93badd539b1b74b3a2d1142cae4fdad4b8e66b75`:
`scripts/d1_build_preflight.py` passed against the saved 01.00 schemas and
the corrected 01.13 and 01.24 type exports. It checks join response, activity
world/map, simulation player, game mode, world-state zone and peer masks,
starter gear, all three unlock-flag tables, and the 80 mission state changes.
For 01.24, the account/character flag capacities are 2,560/256/2,048;
the shifted activity fields and flags roundtrip without omission. All 66
saved 01.00 service request/response handles exist in the 01.24 export.
These checks verify serialization against static type definitions, not runtime
client behavior.

The 01.24 service map was exported on 2026-09-28 from tag `0x80a5e21a`, entry
538 of `ps3_investment_globals_012f_4.pkg`, using `d1_types.py service-map`
and the existing user-supplied Oodle DLL. The 3,432-byte tag contains 94 records
of 36 bytes with element class `0x80801820`. It yields 94 unique wire IDs:
all 66 saved 01.00 IDs and both handles match exactly, plus 28 new IDs. Every
request and response handle exists in the corrected 01.24 EBOOT type export.
The map also records each service name hash for later research. The four update
package files used for the extraction are retained outside this repository;
their SHA-256 values, in patch order `_1` to `_4`, are:

The 94-service map passes `d1_build_preflight.py` with the corrected 01.24
type export and both mission scripts. All 94 default replies encode and decode
with their mapped response type; the same check passes for all 66 saved 01.00
services. Service payload behavior on the 01.24 client remains untested.

The follow-up preflight also found that service 104's response drops the
universe object after 01.00 (01.13 is result-only; 01.24 has a bool at +0x8).
Service 503 still carries it, but its optional fields and flag override list
expanded. The code branch now encodes its populated sign-in reply from the
selected schema; populated replies roundtrip on 01.00, 01.13 and 01.24.

The metadata-only `package_inventory_01.24.json` was generated from Sony's
BLES01857 update file tables using `ps3_update.py inventory`. It records 1,408
package filenames across updates 01.13–01.23, of which 374 are superseded by
the patch-number reset at 01.20. The 1,034 remaining files total 10,305,603,584
bytes. Update 01.24 contains the executable but no package files. This inventory
is a file-presence and size check for an installed copy, not a validation of
package contents or of the game's choice of package patch at runtime.
