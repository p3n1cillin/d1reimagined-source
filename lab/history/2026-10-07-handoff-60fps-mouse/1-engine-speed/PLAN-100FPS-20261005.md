# Plan: Destiny 1 native client at 100+ frames a second

2026-10-05, night, Claude. Target set by the operator: the Xbox One build of this engine runs
well above 100 frames a second in gameplay on comparable hardware; the PS4 build runs natively
here with the whole runtime ours. This plan is shaped by one question only: does a step take
milliseconds off the frame, or remove what blocks taking them off. It supersedes the order of work
in PLAN-TO-60-REV2 (whose measurements it stands on) and the draw-cost note's item list.

## 1. Where the frame goes today, and why that is the wrong architecture

Measured on 2026-10-05 at the stock field of view, Restoration, moving, submit gate open
(REV2 appendix A): the frame is the GPU command thread, about 1.7 µs of CPU per draw times
10,500 draws, about 18 ms. The recording thread runs 1.2 µs a draw behind it in lockstep. The
Vulkan recorder is half idle. The frame pool and present fence never wait: the GPU is not the
limit at 46 flips a second. The game's own work overlaps now that the gate is open.

That 18 ms is spent **reconstructing what the engine already knew** when it issued the draw:
reading its register writes, hashing them, walking its shader descriptors to recover which buffers
and images a draw uses, re-deriving the pipeline per draw, copying its constants and vertex data
into host buffers, and waiting at every constant-engine dump so the copies stay coherent. The
engine had the resource handles, the layout, the shader programs, the dirty bits and the draw
arguments in hand one function call earlier. The Xbox One build hands exactly that to D3D11 and
runs at 100+. On PS4 the same engine hands it to its GNM layer, which turns it into PM4; we then
reverse that. Every item in the draw-cost note shaves that reversal. The plan below stops doing it.

Arithmetic for the target: 100 frames a second is 10 ms. The GPU work of this engine's frame at
1080p on this class of GPU is a few milliseconds (the Xbox evidence; our own GPU time is measured
in section 6). So the whole CPU side, engine, our render layer, the driver, must fit in about
6 ms at 10,000 draws: **under 0.5 µs a draw end to end**, with the engine's own frame work running
in parallel. That number is reachable only when a draw costs a table lookup and an argument
append, not a reconstruction. That is what the engine's own render boundary gives.

## 2. What the native port gives us that the emulator did not

1. **We own the image and the loader.** A hook is a few bytes written before the game starts,
   into functions whose addresses and entry bytes are already pinned for this exact eboot. No
   transactional detour machinery, no exact-build gates at runtime; the loader checks the bytes
   once (as `guest_patches.py` does today) and refuses to start if they differ.
2. **We own memory.** Every direct-memory allocation and mapping the game makes goes through
   `runtime_memory.c`: we know each GARLIC and ONION range, its size and lifetime, and the backing
   is one memfd. The GPU can be given exactly those ranges, in place, on this unified-memory
   machine; what the game rewrites per frame and what is static is observable at allocation and
   at write time, not guessed by page faults.
3. **We own every library call** the engine makes: video-out, GNM submit, labels, sleeps,
   semaphores. The pacing structure of the frame is ours to define.
4. **The engine's render layer is mapped.** The fork's static contract
   (`documents/perf/PS4-ENGINE-FRONTEND-20260912.md`) pins the PS4 counterparts of the Xbox D3D11
   boundary: vertex bind `0x7dcfa0`, index bind `0x7dd1b0`, indexed draw `0x7df950`, nonindexed
   draw `0x7dfb40`, finish/publish `0x7dccd0`, ordered consume `0x7db3e0`, the structured
   descriptor setter `0xfc5bd0` with its per-slot dirty bits, the state-preparation interval
   `0xfc8530` → draw → `0xfc8e50`, and the engine context fields (layout pointer at `+0x1d60`,
   cached handles, the index record with base/type/count). Static call-site counts: 46 vertex
   binds, 20 index binds, 9 indexed and 40 nonindexed draw callers. The fork's build-12 handoff
   (2026-09-13) lists this frontend as its next structural cut; its commits after 2026-09-14 are
   input, multi-instance, LUT and glyph work, so the path was specified and not built [C, git log].
5. **Shaders are already translated offline.** d2-preservation's `offline_xlat` turns GCN programs
   lifted from the shipped packages into SPIR-V with no emulator and no GPU: 3,229 programs from
   package bytes with zero failures, 88% byte-identical to what the emulator's own translator
   produces for the same programs, every module valid; the whole estate (26,777 GCN programs)
   extracted; 26,246 SPIR-V modules produced; HLSL and DXBC behind them for a D3D11 host
   (`runtime/shader-proof/offline-xlat-tool-0001/RESULTS.md`, `status/content/SHADER_TO_PKG_HANDOFF.md`,
   as of their dates; newer counts to be read from the tree). A pre-translated SPIR-V set keyed by
   program hash means no first-visit shader compile on the frame, ever.
6. **Textures are understood.** The PS4 package tiling for this estate is index 13, 1D-thin
   8×8 microtiles in Morton order, parameterised by the 60-byte package header; the detiler exists
   (`status/content/D1_GNM_TEXTURE_DETILING.md`). bbport's texture cache detiles on upload today;
   the same knowledge lets textures be detiled once at creation and never touched again.
7. **The Xbox build is the reference** for every semantic question about the engine's render
   layer: the same functions, the same argument meanings, with D3D11 names on the other side.

## 3. The architecture

Three layers, each replacing a reconstruction with a lookup:

**3.1 Draws from the engine, not from PM4.** Hooks at the engine's render-layer entry points
produce an immutable draw record per draw: the engine's own state version (program handles, the
descriptor-slot contents the setter wrote, the input layout, the bound index record, the vertex
handles and offsets, the render-target and depth/blend state from the preparation interval) plus
the draw arguments. Versions are keyed by the engine's dirty bits and handles, not by hashing
registers. A version resolves once to a Vulkan pipeline and a descriptor set (or a descriptor
buffer offset); every later draw with the same version appends arguments. Per-draw cost: a lookup
and an append.

The existing renderer keeps everything it does well: shader translation (now also the offline
corpus), the texture cache, pipeline creation, barriers, submission. It gains a second source of
draws next to the PM4 decoder, and the decoder keeps running everything the hooks do not cover
(compute, DMA, labels, queries, special passes). Covered draws are executed exactly once: the
hook marks the engine's recording entry so the decoder skips the covered span. GPT's second
handoff §7 to §8 is the correctness contract for this layer (ordered same-frame fallback, exact
once, attachment semantics in the version key, the draw-index ABI for runs).

**3.2 Memory in place.** The GPU reads the game's memory where it is. Buffers bound by handle
resolve to offsets into imported GARLIC memory; constants the engine writes per frame are read
from where it wrote them. No stream copies, no page protection for reads, no constant-engine
drains (the dumps are just writes into memory the GPU will read when it executes). Fences are
written when the GPU completes, which is what the game was built for and what its own ring
discipline assumes. The operator's experience in the fork stands as the risk statement: on a
discrete GPU, in-place reads crossed PCIe and honest fences added latency, and it was not fast
enough. Here there is no PCIe, and the frame is measured in section 6 before any class of data is
switched; the classes are switched one at a time (static GARLIC first: meshes, indices, textures;
per-frame rings last, or kept copied if the measurement says so).

**3.3 Pacing by the game's own clock, presentation when ready.** The Xbox layer runs at 100+
because its render deadline is bypassed while job readiness is kept, its game-time override is
off so the title's elapsed-time accumulator emits simulation ticks on its own, and completion is
reported truthfully. The PS4 engine is the same engine; the fork's clock work pins the sites
(the three constants at `0x5918b3/c7/d1`, the outer deadline at CFG+0x08/+0x28, the terminal
`now_us` call at `0x59395a`, the fixed-step scalar). The port is: deadline removed, a wall-credit
gate at the pinned call so the simulation steps at its rate whatever the frame rate, presentation
when ready through mailbox, no virtual vblank quantisation, honest completion. The counters of
patch 15 and the step witness say whether the simulation keeps real time.

## 4. Order of work, by what it takes off the frame

No calendar. Each step says what it removes, what it depends on, and how it is measured. Steps
within a tier are independent and can be worked in parallel by separate agents; the tiers are
dependencies.

### Tier 0, the enabler (no frame time by itself; everything else needs it)

**The loader hook.** A function-entry or call-site patch into our code with the full register
file captured, for sites whose entry instructions relocate trivially (the fork's pinned spans are
chosen that way; the fork's GPL'd planner/stub in `external/destiny-native-shadps4/src/core/d1_detour_*`
is the reference, and most of it is unnecessary when the image is ours before the game runs).
Exact-build guarded by the entry bytes, like the guest patches. Delivered when a hook at the
nonindexed draw wrapper `0x7dfb40` counts draws per frame and the count matches the PM4 decoder's
for the same frame.

### Tier 1, take the draw path off the frame (18 ms → about 4 ms of CPU at 10,000 draws)

1. **Shadow capture.** Hooks at the four wrappers, the descriptor setter and finish/publish
   record, per draw: handles, layout, index record, setter slots written since the last draw,
   topology, counts. Compared against the decoder's view of the same draw (same ordinal in the
   recording entry): program hashes, buffer addresses and sizes, image addresses, index address
   and count, render targets. Measured as the share of draws whose captured state fully explains
   the decoded draw. This is the learning step the operator named: the engine's own PM4 is the
   teacher; where a field is not yet captured, the comparison says which setter carries it.
2. **Prepared draws from the engine.** The capture feeds bbport's existing prepared-draw path
   (`PreparedDraw`: pipeline selection, sharps, vertex inputs resolved ahead of the decoder), which
   exists today but is switched off because its workers read guest memory at the wrong time. Fed
   by the engine on the engine's thread, at the moment of the draw, the reads are at the right
   time by construction. The decoder then takes the prepared pipeline and bindings for covered
   draws and skips specialisation, sharp walks and register hashing. Expected: the command thread
   from about 1.7 µs a draw to about 0.6; the counter-rule spin stays until step 4.
3. **State versions and runs.** Versions keyed by the engine's dirty bits; draws that share a
   version and differ in arguments become one indirect multi-draw (the fork's active fast path,
   §6.1 of GPT's second handoff: host-generated runs, not the retired compute executor), with the
   draw-index shader ABI and the location-31 refusal rule. Expected: Vulkan calls per frame fall
   three to four times; the recorder's RADV time with them.
4. **Covered spans skip PM4.** The decoder no longer decodes the register and draw packets of a
   covered recording entry; it executes the entry's draws from the records in order with the
   non-draw packets interleaved. Expected: the command thread's remaining decode, apply and
   hand-over cost goes for covered draws; what is left of its time is the uncovered packets.

### Tier 2, take the copies off the frame (the recording thread's 12 ms → a few)

5. **Static GARLIC in place.** Import the game's GARLIC allocations as Vulkan memory (the runtime
   knows them); vertex and index streams bound by handle resolve to imported offsets; no copy, no
   page tracking for reads. Fences at GPU completion for work that reads imported memory. Measured
   first on one class (meshes and indices), with the version check of REV2 §7 on, and the frame
   time before and after; the per-frame rings stay copied until the same measurement says
   otherwise. The constant-engine drain rule disappears for any class read in place.
6. **Textures detiled once.** The texture cache keeps images, but creation follows the engine's
   texture creation (the setter slots and the package header), detiles once with the pinned
   index-13 rule, and never re-uploads a static texture; the write-watch and dirty-page machinery
   applies only to render targets and the few CPU-written images.

### Tier 3, pacing and the ceiling

7. **Shaders from the offline corpus.** Pipeline creation reads pre-translated SPIR-V by program
   hash (the offline translator's output, extended to the whole estate) instead of translating
   on first sight; pipeline libraries and shader objects (the seat exposes both) cut creation
   time; the pipeline cache persists across boots. Removes the first-visit stalls, which are the
   worst frames in any traversal.
8. **Uncapped pacing with real time kept.** The deadline removal and the wall-credit gate
   (section 3.3) as loader hooks; presentation through mailbox when ready; completion honest.
   Measured by the step witness (simulated seconds per wall second 1.00) and the present cadence.
9. **GPU.** With the CPU side under the frame, the GPU is measured per pass (timestamps written
   outside render passes, the device loss of the current profiler fixed first, or
   `VK_KHR_present_wait` for the cadence). Barriers, pass breaks and resolution are tuned against
   the measurement; the fork's Nsight lesson applies (hundreds of wait-for-idle drains a frame
   can be the GPU's whole cost).

### Not on the critical path, done with the hook once it exists

Mouse through the engine's own keyboard-and-mouse layer (enable byte `0x1abbc53`, publish the
state block at `0x1abc3e0` on the builder's thread at `0x924cc5`, the look/cursor/assist hooks the
fork's record lists); the simulation-step witness; the 1 µs `usleep` loop the game spins at up
to 90,000 calls a second (51 µs each on Linux), to be answered with a short spin in the runtime so
a core is not burned in the kernel.

## 4a. The steps, in order (each: mechanism, then the check that it worked)

1. **Setter capture.** Hook `0xfc5bd0`; print stage, slot, count, the 16-byte descriptor.
   Check: the words are V#/T#/S# shapes (guest base addresses, strides, formats); setter calls
   per frame are of the order of draws × resources.
2. **Line the engine's slots up with the shader's resource table.** The setter writes
   16·count bytes at word index `stage·0x642 + slot·4 + 0x4c0` of the state backing; that
   backing is the CPU image of the constant RAM the CUE dumps; the decoder sees the same bytes
   arrive through `DumpConstRam(offset, size, address)` and reads them back as the shader's
   flattened user data (`Info::RefreshFlatBuf`). Mechanism: print both sides for the same draw,
   keyed by the draw packet's address (the command buffer's write pointer at the emit hook; the
   packet header the decoder reaches): the hook side with the shadowed slots of the stages in
   use, the decoder side with the flat user data and the resolved sharps. Check: the setter's
   words appear verbatim in the decoder's flat buffer at a fixed offset per (stage, slot); that
   offset table is the result.
3. **Build the flattened user data on the engine thread.** From the shadow table the setter
   hook fills, plus the user-data registers the preparation interval writes (the packets between
   the previous draw and this one, parsed on the engine's own thread at the moment they are
   final). Check: byte-identical to the decoder's flat for the same packet address, as a hit rate
   per frame; a mismatch falls back to the decoder's path, so this is slower-not-wrong until the
   rate is 100%.
4. **Feed bbport's prepared-draw path from it.** `PreparedStage` holds program, flat user data,
   the sharps read from flat in the program's resource order (`PrepareResources`), vertex
   inputs; the code that fills them exists and is thread-safe (written for the workers). Only the
   input changes: the engine's flat instead of a speculative replay. The GPU thread's acceptance
   check exists (`flat` matched word for word → the prepared program and sharps are used,
   `UsedPrepared()`). Check: `UsedPrepared` rate per frame toward 100%; command-thread CPU per
   draw falls by the specialisation constructor, its compare, `GetProgram` and `GetSharp` (about
   18% of the thread today). **Frames appear here**: the command thread under the game's
   16.683 ms deadline turns the alternating one-and-two-period frames into one period each.
5. **Drop register hashing for engine-fed draws.** The checksum only validates speculative
   workers; engine-fed draws are validated by the flat match. Check: `HashRegisterPacket` gone
   from the profile (about 4%).
6. **Record the draw at the boundary instead of decoding it.** The emit hook has the packet
   address; the decoder, on reaching a packet with an engine record, takes pipeline, bindings and
   arguments from the record and skips decode, apply and hand-over for it. Check: command-thread
   time per covered draw is packet assembly only; draws per frame unchanged; picture unchanged.
7. **Versions and runs.** Draws with the same engine state version (no dirty bits between them)
   become one indirect multi-draw. Check: Vulkan calls per frame fall; the recorder's RADV share
   falls; picture unchanged.
8. **A cheap upload path (memory in place only where the hardware allows it).** The users
   run discrete GPUs on Windows, where vertex and index bytes must cross the bus: the general
   design is the one D3D11 drivers use, one memcpy per draw into a persistently mapped upload
   ring, pooled allocations instead of a `vkAllocateMemory` per residency step (bbport already
   links VulkanMemoryAllocator), no per-draw locks, fewer and larger submissions. Importing
   guest memory as Vulkan memory (`VK_EXT_external_memory_host`, the fork's `uma_import`) is an
   option for unified-memory parts only, measured on its own. Check: the recording thread's
   µs a draw, its memmove share, allocations a frame; picture unchanged.
9. **Shaders from the offline corpus, pipelines persisted.** Check: zero shader compiles in a
   traversal.
10. **Pacing by the game's clock.** Not last: a precondition for any frame gain above 60 to
    be honest. The fork's record (`documents/d1-outer-wake-5994.md`, A5 run) shows the PS4
    engine's fixed domain is outer-driven: one physics tick per outer-loop entry, no wall
    correction, so with our 60 Hz constants (physics `h` = 1/60, kept: that is the chosen
    trade) game time follows the outer rate, about 0.72–0.80 of real time at today's 43–48
    entries a second, 1.67× at 100. In order: (a) a step witness in the loader (Havok wrapper
    `0xcace80` entries a second and `h`), because the native client has none; (b) the fork's
    wall-credit gate at the pinned terminal `now_us` call `0x59395a → 0x592820`, ported as a
    loader hook with the rate knob at 60: sixty entries a second carry a tick, the rest are
    zero-advance frames, presentation when ready; (c) the end state, delta time: the engine's
    own elapsed-time accumulator emitting ticks from wall time, as the Xbox layer runs it with
    the game-time override off, the fork's fixed-step-owner machinery
    (`SHADPS4_D1_FIXED_STEP_ENABLE`) is the lead. Check: the witness at 1.00 simulated seconds
    per wall second at every frame rate; presents at whatever rate the frame allows.

Frames move at 4, again at 6, 7 and 8; 10(b) must be in before the rate passes 60.

## 5. What stays from the measurements so far, and what retires

Stays: the counters (patch 15), they are the measurement of every step above; the open submit
gate (patch 17); the shadow-helper, stencil-alias, masked-clear and view-fallback ports (picture
correctness, unchanged by the architecture); the label release; the patch series and the walk
tooling; the PM4 decoder itself, as the uncovered-packet path and the oracle for shadow capture.

Retires as coverage grows: the constant-engine ordering rules (both; they exist only because
copies exist), the stream copies, the register hashing and specialisation per draw, the
draw-preparation workers (replaced by the engine feeding the same structures), the frame watcher
as a correctness instrument (the version check and the shadow comparison replace it).

## 6. Measurements that gate each step

- Frame: flips a second and the interval distribution from the present thread; later host
  presents through `present_wait`.
- Per thread: the `Frame stats` CPU per draw, idle, waits by cause; per-stage profiles as in REV2 appendix A.
- Coverage: draws captured by the hooks against draws decoded, per frame and per call site.
- Correctness: the shadow comparison (field by field), the version check (decode-time bytes
  against record-time bytes for every buffer class), the release ledger for in-place memory, the
  operator's eyes, and the frame watcher only as a smoke alarm.
- Simulation: steps a second and simulated seconds per wall second from the step witness.
- GPU: per-pass timestamps once the profiler is repaired, or present cadence meanwhile.

## 7. First steps

The critical path starts with the hook, so the first steps are the hook and the first shadow number:

1. The loader hook at `0x7dfb40` and `0x7df950` (the two draw wrappers) with register capture;
   bytes checked against the eboot before the patch is written.
2. A counter and a sampled record (every Nth draw: context, topology, count, index record, the
   cached vertex handles and offsets) printed with the frame statistics.
3. The same frame's decoded draw count beside it: if the two agree, the engine's draw path is
   covered by two functions and Tier 1 is a matter of capturing state, not of finding draws. If
   they do not, the difference names the other callers.

Then the descriptor setter `0xfc5bd0` hook with its slot and stage, and the first field-by-field
comparison with the decoder for one draw family. That is the point at which the per-draw cost
starts falling, and from there each tier is measured by the same counters that found appendix A's
numbers.
