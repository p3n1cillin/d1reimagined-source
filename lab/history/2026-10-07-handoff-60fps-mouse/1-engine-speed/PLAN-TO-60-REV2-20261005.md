## 1. The verdict, accepted

The review's central objection stands: "the renderer has room for 60" was an inference from two
averages (the command thread's idle counter and per-thread CPU use), and the code shows at least
three ways those averages arise with the renderer, not the game, as the limit. So the first plan's
order (find what the game waits for, then renderer speed) is withdrawn. The replacement order is:
make the counts mean what they say, trace the dependency chain of a slow frame, then follow it
wherever it points, with the two pacing changes under a proof obligation the whole time.

What stays: measurement first; the picture work can run in parallel; stock 30 Hz remains the
setting that is known to run the game at its own speed on this machine today.

Two more facts the review did not have, both read first-hand today:

- **The game waits for the previous frame's GPU completion before it submits.** The fork pinned
  it (`src/core/d1_submit_overlap.{h,cpp}`): a loop at eboot `0x7db540` that polls a completion
  label against a target sequence, steals a job from the job system when it can, and otherwise
  sleeps 300 µs; the detours sit at `0x7db54a` and `0x7db7c3`. The 48 bytes of that loop are
  byte-identical in the eboot the native client runs [C, read from `out/eboot.elf` on the seat].
  The fork's experiment of submitting before that wait is off in its play profile.
- **The HLE adds its own gate**: `sceGnmSubmitCommandBuffers` and `sceGnmSubmitDone` call
  `WaitGpuIdle()` (`gnmdriver.cpp` 87, 2298, 2342, 2359); `submission_lock` is set when
  `SubmitDone` finds the GPU busy and cleared by the GPU-idle interrupt, which bbport raises
  only after the recording thread has drained and deferred fences are written
  (`liverpool.cpp` 170–187) [C].

## 3. Corrected statements

- Every "FPS" in the first plan and the inventory is **virtual flips a second**: requests taken
  by the present thread at 60 Hz ticks. Host presents and displayed frames were not counted.
- "The renderer is not the limit at about 10,000 draws" is replaced by: at the stock field of
  view, submissions are intermittent and the average CPU demand of each renderer stage is below
  one core; the limiting dependency is unidentified.
- "Nothing measures GPU time" is replaced by: GPU time has not been collected for this scene.
- "Until 60 is held, stock 30 Hz is the setting at which the game runs at its own speed" is
  replaced by: stock 30 Hz is the only such setting **in the native client today**; the fork
  documents a second (stock constants, outer wake, flip-rate probe, fixed-30 wall gate) that
  this client has not ported.
- The frame-rate table of the first plan stands as reported observations, with two caveats: the
  numbers are virtual flips, and the capture tool's cost was not controlled.

## 4. Hypotheses for the missed frames

Not mutually exclusive; several can hold at once. Each has a discriminator that costs no code
or little code. For intervals of one or two 60 Hz ticks, `FPS = 60 / (1 + q)` with `q` the share
of two-tick frames; 39 to 48 corresponds to `q` of 54% to 25% (the review's consistency check).

| | Hypothesis | Mechanism in the code | First discriminator |
|---|---|---|---|
| H0 | Host GPU, frame pool or swap thread hold the recording thread | section 2, finding 2 | `BB_GPU_PROFILE=1` run; frame-pool and `present_done` wait counters on the recording thread; `BB_PRESENT_THREAD=0` control |
| H1 | Flips shown only on 60 Hz ticks cost two ticks for a frame slightly over one | `PresentThread` 703–724 | paired fresh-process runs `BB_FPS_LIMIT=0` vs `60` at `BB_VBLANK_HZ=60`, all else fixed; log the game's flip rate |
| H5 | The game's own pre-submit wait (section 2) serialises its command building with the renderer's decoding and recording | `0x7db540` loop; fences written by the recording or Vulkan recording thread | split the command thread's idle time by position in the frame (first submission after a flip against the rest) and histogram the gap from "idle begins" to "next submission arrives"; sleep accounting by guest call site |
| H6 | The HLE's `WaitGpuIdle` gate | `gnmdriver.cpp` | time the guest spends blocked in it, per frame |
| H2 | Runtime kernel objects delay woken threads | `runtime_sema.c`, `runtime_mutex.c` | wait accounting by call site (count, requested, actual); only then `perf sched` |
| H3 | The game's outer loop | fork clock notes | outer-call counter at `0x59395a` against submissions and steps |
| H4 | Another stream wait | `WaitRegMem` paths | command-thread time in non-label `WAIT_REG_MEM` and fence waits |

Order of testing: H0 and H1 first (no code; one run each), then the counters that serve H5, H6
and H2 together (one build), then H3 and H4 if time remains unexplained.

### 5.2 Instrumentation, two layers (existing files only until decision 4)

Layer 1, counters printed with `Frame stats` (cheap, always on):

- recording thread: time in `GetRenderFrame` (free frame; `present_done`), time in
  `SubmitFlipInternal`, pipe-full waits; swap thread: queue depth, acquire time, present call
  time, skipped frames, present IDs and their `present_wait` times;
- command thread: idle split by position in the frame and a histogram of the gap from idle to the
  next submission; drain spin time by reason (exists; print it); submissions per frame;
- guest side: time blocked in `WaitGpuIdle`; sleeps, semaphore, mutex, condition-variable and
  event-queue waits by guest return address (count, requested, actual), top entries;
- video-out: the game's requested flip rate, display buffer count and index sequence, present
  mode and image count, `label_generation` releases by rule;
- constant engine: a count of waits where `de != ce` after the yield loop (should be zero under
  the pinned loop; if not, the model of section 2 is wrong).

Layer 2, the event trace: the review's schema (monotonic time, frame id, submission id, object or
address, generation or ticket, thread, event, outcome), preallocated per-thread buffers, a dropped
count, written to a file on request or at exit. Identities: the frame id is the flip sequence;
the submission id is the guest's submit count; both travel in the draw pipe packets and the
recorder chunks. Acceptance: an instrumented run and a plain run agree within a measured
overhead; the trace shows queue backlog and lost events explicitly.

From the trace: arrival interval, frame latency (first submit to host present), per-stage CPU
service, GPU span, throughput of unique host presents, backpressure. A slow interval is explained
by walking its predecessors in the trace, not by subtraction.

## 7. The two correctness instruments

The review is right that minutes of clean frames prove nothing about ownership. Two instruments
test the invariants directly; both are diagnostic modes, off for timing runs.

1. **Decode-against-record version check.** At decode the command thread already resolves each
   stage's buffer descriptors for specialisation; in this mode it hashes the first bytes of each
   constant and vertex range and puts the hashes in the draw packet. The recording thread hashes
   the same bytes when it reads them and counts mismatches (draw, range, positions). A mismatch is
   exactly the failure both pacing rules could cause: a draw consumed a different version than
   the one the game's contract promised at decode. Ranges overlapping a pending in-stream GPU write
   are reported apart (their decode-time view is legitimately older). Positive control: toggles 13
   and 14 produced wrong frames reliably; with them on the counter must fire. Then forced delays:
   a per-packet sleep on the recording thread, a delay in the copy workers and in the Vulkan
   recorder, a delay in the swap thread, each alone; the counter must stay at zero under every
   one with the pacing rules on.
2. **Release ledger for the label.** Every deferred guest-memory read (copy workers, deferred
   uploads, recorder-side copies, readbacks) carries the frame id at which it was queued; at
   execution it checks that the label generation covering that frame has not been released. The
   invariant per display-buffer generation: all reads of the bytes it gates have consumed them,
   all asynchronous writes into them have retired, the GPU holds retained host storage, and the
   pending present retains its image. The audit that precedes the ledger lists every reader of
   guest memory in the renderer by name and says which thread runs it and what bounds it.
   Occlusion landings (section 9) are a new writer and join the ledger before they ship.

Constant engine, in addition: an epoch and the exact counter value stored with each saved
position; a full drain whenever they do not match; a short packet trace (counters, nested
boundaries, dump destinations, positions) from one real frame, replayed offline against both
arithmetic models with a lagging consumer.

Acceptance for both pacing rules: zero version mismatches and zero ledger violations under every
forced delay, then the soak. Until then they stay switchable and are reported as observations.

Conditional cases, each armed the day its piece is ported (from GPT's second handoff §7 and §12):
with stage or prepared-state reuse, a Linux dirty-tracking protocol must not lose a write between
scan and re-arm (the soft-dirty race) and must fail closed; with multi-draw runs, a fragment input
at the generated draw-index location must select a safe interface or the single-draw path, never
block zero; range keys must carry attachment semantics (depth and stencil access, generations,
views, load and store behaviour); every refusal (capacity, cold miss, unsupported primitive)
executes the draw once, in order, in the same frame; with borrowed guest memory, release follows
the GPU's last read, not the host's.

## 8. Simulation check and the target

The target is a combination, not a number. Proposal for decision 5: the 59.94 Hz pump as the
manifest has it; simulated seconds per wall second 1.00 ± 0.01 (the fork's havok meter definition:
sum of steps × h); unique host presents at the pump rate with the distribution rules of
section 11. To measure it the client needs the step witness: a counter at the fork's pinned step
wrapper (its `d1_havok_meter`), and the outer counter at `0x59395a`. Both are guest call-site
hooks, exact-build guarded like the guest patches (`Original=` bytes); one small general mechanism
(a call-site thunk that counts or adjusts an argument) serves both and, later, the fixed-30 wall
gate if the operator wants that alternative (decision 7).

## 9. Picture

- **Occlusion**: before building, trace what the game actually sends: predication operations,
  the draw-visible and continue bits, how many backend pairs are valid, how often it polls and
  gives up. Then counts with readiness and lifetime rules (payload before valid bit; a sequence
  number per block; retire on reuse or unmap), and GPU predication from a stable 32-bit value
  in a host buffer written by `vkCmdCopyQueryPoolResults` (transfer write → conditional-rendering
  read barrier), inverted through the extension's flag, unsupported combinations failing open and
  counted. The seat exposes `VK_EXT_conditional_rendering` [C]. No ordinal hint presented as exact.
- **Red ambient in `mission_elevator`**: reader first (producer, allocation generation, consuming
  buffer and offset, pitch, tiling, format, synchronisation); independent of the pacing work.
- **Rechecks**: the descent with the masked stencil clear; `cine_speaker`.

## 10. Fork on the seat and the renderer gate

A portable configuration of the fork on the seat, listing which of its facilities activated, at
the fixed spawn view with the same controller routine; paired runs; distributions, not a maximum;
realised FOV, resolution, present mode, cache state recorded. Needs decision 3 for the account;
build and inspection do not. A faster fork is a reason to assess a transplant (interfaces, memory
import dependencies, result visibility, retirement), not proof it is cheaper.

Gate, as sharpened by GPT's second handoff (§6, §11 Phase E; see
[RESPONSE-RENDERER-FLOW-20261005.md](RESPONSE-RENDERER-FLOW-20261005.md)): the fork's active fast
path is host multi-draw with versioned preparation, and it depends on nine coupled pieces, so the
choice is between a **coherent unit behind a narrow native adapter** (memory identity, immutable
draw and event boundary, retirement) and the **whole pinned donor renderer behind the same
adapter**, decided by the smallest implementation that shows correct output, bounded lifetimes and
a measured gain. "Port the command processor" is not an instruction. The retired
device-generated-command executor is not imported.

## 11. Acceptance and stop rules

For the chosen rate and field of view: elapsed time, unique presents, interval histogram with
p50/p95/p99/p99.9/max, missed opportunities, longest run of misses, latency, queue depth over
time, simulated seconds per wall second, capture coverage, confirmed corruption. Stable gameplay
reported apart from transitions; transitions tested explicitly (loading, orbit to world, the
descent, `mission_elevator`, `cine_speaker`, menus and HUD, combat and bodies, restart). A detector
alert suspends acceptance and preserves the clip and trace; a confirmed corruption rolls the
change back in the play configuration and keeps the reproducer for diagnosis. The soak (an hour
each at the 60 Hz set and at stock 30) is exposure, after the forced-delay tests, not instead of
them.

## 13. Where this revision is weakest

- H5 is a hypothesis from reading the fork's source and matching bytes; nothing here has measured
  how long the game spends in that loop under this runtime.
- The version check assumes decode-time bytes are the intended version for every buffer class;
  in-stream GPU writers are handled by exclusion, which may leave a class unchecked.
- The present-wait and GPU-profile numbers depend on a driver and compositor nobody has
  characterised for this purpose; their own overhead is measured in 5.1.
- One machine, one mission, minutes; the fork comparison not yet run.

### A.4 What this says, and what it does not

- At the stock field of view **neither pacing change moves the flip rate** within noise. The
  label release turns 8 to 10 ms a frame of label wait into command-thread idle, one for one; the
  counter rule turns drain time into idle. The first plan's rises (35 → 40 → 42–48) were at
  FOV 105, where the renderer was the limit; here it is not, and the command thread is idle 43%
  of the time with both rules on while most frames still take two ticks.
- A frame is one tick or two, never between. With the renderer's pipeline at about 13 to 15 ms
  for a frame and the game starting its next frame only after the flip event at the tick, the
  period is `ceil((R + G) / 16.7 ms) × 16.7 ms` with `R` the renderer's time and `G` the game's
  time from the flip event to its next submit: whenever `R + G` crosses 16.7 ms the frame costs
  33.3 ms. The measured mixtures (37 to 46 flips/s) fit `R + G` straddling one tick [I]. This is
  H1 together with the game's own handshake; it is a model, not yet a measurement of `G`.
- The decisive test needs no code: `BB_FPS_LIMIT=60` (a flip shown when it arrives, so the game
  gets its event at `R` instead of at the next tick). If the model holds the flip rate rises to
  about `1000 / (R + G)` with uneven intervals; if it does not move, the game waits on something
  other than the flip event (vblank waits, its own deadline, or the HLE gate). Started next.
- Per-draw cost still matters because it sets `R`: with margin for `G`, `R` must be about 11 ms
  at the stock field of view (about 1.0 µs a draw through the pipeline) and about 8 ms at FOV
  105, unless the game is allowed to run a frame ahead (flip event delivered when the flip is
  queued, under the same ownership proof as the label; decision 2 and section 7).

### A.7 The counters build (patch group 15), in the world, moving, stock field of view

Two 5 s windows at 38 to 44 flips/s, 9,500 to 10,500 draws a frame, command thread idle 18 to
40%, 35 to 38 submissions a frame:

- **Guest in the sceGnm submit gate: 8.1 to 9.2 ms a frame, 0.9 waits a frame.** This is the
  HLE's `submission_lock`: `sceGnmSubmitDone` arms it whenever the renderer is still busy, and
  the guest's next submit then blocks until the renderer is idle.
- Command-thread idle gaps that end with a submission: the first of a frame is under 0.25 ms
  nine times in ten (196 to 205 of 216 to 228) and 16 ms or more the rest (20 to 23); within a
  frame they total 0.15 ms. So the game submits the moment the gate opens, and the renderer gets
  the next frame the moment the game submits: **the two alternate instead of overlapping.**
- Recording thread: frame pool 0.00 ms, present fence 0.00 ms. H0 (GPU, pool, swap) is out at
  this field of view.
- The command thread's own CPU time is 1.63 to 1.76 µs a draw, about 17 ms a frame at this draw
  count, with the counter rule's drains inside it (17% of the thread, A.2).
- Guest waits by call site (eboot address = site − 0x800000000): `0xf52ae`, 78k to 82k timed
  semaphore waits a window asking 1.1 ms and sleeping 0.37 to 0.39 ms (the job threads idling);
  `0xff67a0`, 30 waits a second of exactly 33 ms (a 30 Hz service thread); `0x9288cc` and
  `0xb48472`, 200 Hz polls; `0x804745`, 2 Hz; `0x7e383a`, 33k to 93k `usleep(1)` calls a window
  that sleep 51 µs each (the kernel's minimum): a poll loop whose cost the runtime controls.
  The pre-submit completion poll at `0x7db54a` is not among the top six: the game spends its
  wait in the HLE gate instead.

Reading: at the stock field of view the period is about **R + W**, the renderer's time for a
frame (about 17 ms of command-thread CPU, lockstepped with the recording thread) plus the game's
own frame work after the gate opens (about 6 to 8 ms), because the gate serialises them. Two
changes follow directly, both built as patch groups 16 and 17 and run next:

1. **Patch 17, the submit gate**: `sceGnmSubmitDone` no longer arms the lock. The guest already
   waits for the previous submission's completion label before each submit (the fork's pinned
   loop), which bounds its run-ahead, and its fences are written in stream order when the
   recording thread reaches them, so memory it reuses after a fence is no longer read; the same
   ownership proof as the label release, with the same open obligations (section 7).
   `D1_GNM_GATE=stock` or toggle bit 61 restores the rule. Expected: W overlaps R; the period
   falls toward R.
2. **Patch 16, dump read tracking**: the counter rule is replaced by the exact one (a dump waits
   only for a read of that memory the recording thread still has, tracked by stage A), which
   frees stage A from the recording thread's pace. Toggle bit 60 restores the counter rule.
   Expected: R falls by the drain share and by whatever overlap the lockstep cost.

If both hold, R must still fit under the game's own 16.683 ms deadline for a locked 59.94; that
is the per-draw work of the draw-cost note.

### A.9 The in-world A/B of the two rules (fresh boot under the stock rules, moving, one process)

| state | flips/s | A idle | A CPU a draw | submit gate | dump waits/s | pacing |
|---|---|---|---|---|---|---|
| stock rules | 43.6 | 26.2% | 1.63 µs | 5.03 ms a frame | 39.6k | median 16.7 ms, 82 over 1.5× |
| gate off, counter dump rule | 46.6 | 15.7% | 1.70 µs | 0.00 | 44.4k | median 16.7 ms, 67 over 1.5× |
| counter rule off (exact dump rule), stock gate | 36.2 | 0.7% | 2.62 µs | 20.7 ms a frame | 0 | median 33.3 ms, p99 66.7; A blocked on GPU ticks 35.5% |
| both new | 38.6 | 1.2% | 2.46 µs | 0.00 | 0 | median 33.3 ms, p99 50.0; GPU ticks 35.7% |

Findings:

1. **Patch 17 (the gate) behaves**: its wait is gone, pacing is unchanged, the flip rate is a
   few higher (within the scene's noise), and the command thread's own CPU time, about 1.7 µs
   × 10,500 draws ≈ 18 ms a frame including the counter rule's spin, is now plainly the frame.
   The operator's eyes on it in the world are the remaining check (A.8's flashing was with both
   new rules on).
2. **Patch 16 (the exact dump rule) is wrong as built and stays off.** With it, no dump ever
   found a tracked read (0 waits), yet with both new rules the picture flashed (A.8). So the
   reads the counter rule protects are not the tracked classes (buffers over 16 KiB, index data,
   DMA sources, indirect arguments): they are **vertex streams or textures the game feeds through
   constant-engine dumps** [I, strong]. Freed of every wait, the command thread then ran ahead
   until it blocked on GPU completion a third of its time and spent 0.9 µs more CPU a draw.
   Lesson: the game's own ring discipline (a wait within a few groups) is the exactness level
   the console needs, and emulating its constant engine on the decode thread makes the two stages
   run in near-lockstep by design. The way out is not a looser wait but **copying at decode
   whatever the dumps feed** (constants already are; vertex streams that overlap a recent dump are
   the next class), so the recording thread never reads dumped memory. Design noted in the
   draw-cost note; the counter rule stays until then.
3. The "GPU ticks" wait that appears when the command thread runs far ahead names a third
   dependency on that thread (a wait for GPU completion before some resource is reused); which
   site, is open.
