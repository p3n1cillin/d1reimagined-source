After A Guardian Rises, the client now goes CONTINUE → the reveal (165) → the Tower by its own
choices, in the live order. That closes F20 ([full-game test](ps4-56578-full-game-test-2026-11-06.md))

## What was missing

The [script-bridge note](ps4-56578-script-bridge-2026-11-05.md#run-fg2j-still-orbit-the-end-of-the-activity-message-for-message-against-live)
compared run fg2j with the live A Guardian Rises capture and listed the likely differences. Two
turned out to matter:

1. **The client must launch 165 itself.** The lab's `D1_AH_ACTIVITY_REMAP=164:165` serves the reveal
   under A Guardian Rises' launch, and a cinematic's follow-on comes from the activity the client
   launched.
2. **Field [6] must name the reveal and then be cleared.** Live set the profile's current activity
   to the reveal (completed 0) at the join. It cleared it to `ffff` in the push that answered the
   client's 104 after the 8. The live client sent its own matchmaking for the Tower 0.1 s later.
   The script bridge does both (`started`/`ended`, the F20 changes). A step schedule did neither.

## The change

- **Steps record the start and end of the activity they complete** (`state.rs`, `advance_mission`).
  For a schedule whose steps carry `complete=`:
  - its first step calls `ActivityRewards::activity_started`;
  - for a cinematic completion, the step whose list sets lifetime 8 (`@phase 8`, now kept on
    `MissionStep::lifetime`) calls `activity_ended`.

  These are the script bridge's own calls, so the store runs `started`/`ended` as before (field
  [6] completed 0; `ffff` with the reply to the next 104).
- **`next=INDEX:HASH`** on a `complete=` step records the hand-off (`activity_hand_off`), as the
  bridge's `reward` does. It is bookkeeping only: no server message names the Tower.
- **World tables:** `world-table-cine-live.txt` serves index 1 as the Tower, with the same lists
  as index 0.
- **Lab stand-in:** `lab-agr-quick-then-reveal-steps.txt` serves A Guardian Rises and completes it
  60 s after the spawn wait (gameplay chain, lifetime 6, then 7 with the post-game authority). The
  real chain can then be tested in about 12 minutes:
  - the post-game screen;
  - CONTINUE;
  - the client's own launch of 165;
  - the reveal;
  - the Tower.

  It is not retail timing.

## Still open: the Tower after the reveal

After the reveal, the client launches the Tower and reaches `in_world` in private slice set
PRV00.00. It advertises its private Tower session, then reports nothing more (no 566, 3615 or
2014) and the screen stays black. Ruled out:

- **The public host:** rev9b ran the same chain with `D1_AH_PUBLIC_HOST=0` and stalled the same way.
- **The Tower's lists:** loaded first (rev8a, `D1_AH_ACTIVITY_REMAP=164:1`), the same world-table row
  spawns the Guardian in Tower North within 20 s (566, 3615, 2014, then slice set 24).
- **The host's frames:** the sensor stamps restart at tick 0 for each world. The host's log for the
  Tower is the same in rev8a and rev9b up to the client's spawn.
- **Field [6] naming the Tower:** live set it about a second after the Tower join. Written 4 minutes
  late in rev9b (`started … 0xdf283afb`), it did not wake the client. Whether it must come at the
  join is still to test.

The live capture (Social.Tower, 7 Nov) shows a client joining a Tower host (join type 2) into
slice set 24.
