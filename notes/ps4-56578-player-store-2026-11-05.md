# PS4 56578: the persistent player store and progression (5 November 2026)

Offline work: built and unit-tested only. Nothing here has been run against the game yet.

The responder can now keep a Guardian between sign-ons: the account, its characters, their
inventory, equipment, currencies, completions, unlock flags, checkpoints and progression. XP and
rank curves, vendor reset times and refund rules come from Bungie's final D1 manifest. The store is
**off unless `D1_STORE=1`**. With it off, every path serves the fixture knobs exactly as before.

Code: `ps4/d1-server/crates/d1-responder/src/player_store.rs` (the store and its trait) and
`src/progression.rs` (curves, schedules, refund policies, rewards, profile edits). Tables:
`ps4/fixtures/56578/progression/`.

## The model: Bungie's world server

Bungie's GDC 2021 talk ("Exploring Services Architecture at Bungie") describes the D1-era design:
an in-memory WorldServer holds each signed-on character, saves every five minutes and at once on
important events, and keeps characters as rows of attributes. The store follows that design:

- One record per account, held in memory while the responder runs.
- **Important events save at once** (`PlayerStore::save_now`): vendor purchases (901), equips
  (403), dismantles (402), loot grants, profile and account pushes the client received, activity
  completions, unlock-flag changes, checkpoints and control commands.
- **Everything else marks the record dirty** (`PlayerStore::mark_dirty`). For example, a decoded
  profile that only refreshes the summary. A background thread saves dirty records every
  `D1_STORE_SAVE_SECS` (default 300, the talk's five minutes). An important save also writes
  whatever was waiting, and the history line lists those changes.
- Open `attributes` maps on the account, each character and each item hold anything a later
  service needs, without a schema change.

## Files and crash safety

Everything lives in `D1_STORE_DIR`, outside the repository. The default is
`%LOCALAPPDATA%\d1reimagined\player-store`, or `$HOME/.d1reimagined/player-store`.

| File | Holds |
|---|---|
| `identities.json` | player name -> account, character and profile SOIDs |
| `account-<soid:016x>.json` | the account record (schema 1, below) |
| `….json.prev` | the record before the last save |
| `….json.corrupt-<unix>` | a record that didn't parse, kept aside (see below) |

Every write goes through `atomic_write`:

1. Write `<file>.tmp` and `sync_all` it to the disk.
2. Copy the old file to `<file>.prev`.
3. Rename `.tmp` over the file. The rename is atomic on NTFS and POSIX file systems.

A crash at any point leaves either the old record or the new one, never part of one. A `.tmp`
left by a crash is ignored, and the next save replaces it. If a record doesn't parse (a disk fault,
or a hand edit gone wrong), the store moves it aside to `.corrupt-<unix>` and reads `.prev`. If
neither parses, the store refuses to start: it serves the fixtures and leaves both files alone. It
also refuses a record whose schema is newer than its own, and leaves that record untouched.

## Identity (shared with stream H)

`identity_for(dir, player, first)` gives each player name a stable identity, allocated once and
never reused:

- The first player (by default `local`, set by `D1_STORE_PLAYER`) gets the responder's own knobs:
  `D1_ACCOUNT_SOID`, `D1_CHARACTER_SOID` and `D1_PROFILE_SOID`, defaults `0xD100_0000_0000_0001`,
  `…0101` and `…0201`. So turning the store on changes no SOID the client sees.
- Player *n* (n ≥ 1) gets `0xD101_0000_nnnn_n001` (account), `…101` (character) and `…201`
  (profile). This range is outside the `0xD100_…` range that the knobs, the inventory items
  (`…0301`+) and purchases (`…0601`+) use.

`Store::open_player(dir, player, first, sources)` opens that player's record, seeding it from the
fixture knobs on first sight. Stream H's multiplayer sessions should name players through
`identity_for`. They shouldn't mint SOIDs of their own.

## The record (schema 1)

- `account`
  - `payload`: the served account object.
  - `slots`: currency slots, `slot -> (content, quantity)`.
  - `unlock_flags`: the list served on 503/205.
  - `next_item_soid`.
  - `refunds`: account field [20].
  - `vendor_resets`: vendor hash -> last reset seen.
  - `grimoire`: card -> score.
  - `attributes`.
- `characters["0x…"]`
  - `profile`: the payload, byte for byte.
  - `profile_object`: decoded, 29,560 B.
  - `profile_stale`: the object was edited since it was encoded.
  - `character`.
  - `items`: family-4/3 elements in serving order.
  - `roster`: cards.
  - `summary`: XP, level, prestige, equipped items, slots, activity and completion subs, read from
    the object.
  - `current`: activity and XP at its start.
  - `completions`.
  - `checkpoints`.
  - `progress`: reputation totals by progression name (authoritative; see "Reputation" below).
  - `reputation_pending`: grants made while no profile object was decoded, as deltas.
  - `light`.
  - `bounties`.
  - `attributes`.
- `history`: the last 200 changes. `revision`: bumped by every save. `seeded_from`: the knobs it
  was seeded from. `player`.

**Seeding.** On first sign-on the store reads the files the knobs name (`D1_PROFILE_FILE`,
`D1_ACCOUNT_FILE`, `D1_CHARACTER_FILE`, `D1_INVENTORY`, `D1_ROSTER_DIR`, `D1_UNLOCK_FLAGS`,
`D1_VENDOR_ACCOUNT_SLOTS`). It uses the same readers as the serving code, so its first serve is
byte-identical to the fixtures. A unit test builds the family-4 baseline both ways and compares
them. After that first sign-on, the store is the source.

## Hooks in the responder (all behind `D1_STORE=1`)

| Path | With the store on |
|---|---|
| Family 4 (profile, account, inventory items) | serves the store's profile, account and items |
| Family 3 (character) | serves the store's character |
| Roster families | serves the store's cards (the loot grants' cards are added) |
| 503/205 unlock flags | serves the store's list (completions and `unlock` commands change it) |
| 901 purchase, 403 equip, 402 dismantle (vendor.rs) | starts from the store's profile, slots, next instance and refunds; writes the result through and saves |
| Refund records | D1's rule: Eververse and Silver Dust only, 15 minutes (below) |
| Profile, account and loot pushes delivered | recorded; the profile is decoded, and activity starts and completions are noted |
| Sign-on | vendor resets since the last session are logged; a stale (edited) profile is re-encoded |

## Progression from the manifest

`tools/ps4_setup/d1-progression-tables.py` reads Bungie's final D1 manifest as DIM archives it
(`d1-manifest-base.json.gz`, with `d1-manifest-strings-en.json.gz` for names). The manifest is
Bungie's data and stays a local input. The script writes three compact tables, each headed with
the definition it comes from:

- **`progression-curves.tsv`** (`DestinyProgressionDefinition`, 26 curves). `character_level`
  (hash 1716568313) has 40 steps that sum to **346,000 XP at level 40**. `character_prestige`
  repeats 25,000. The table also holds every faction (Vanguard, Crucible, Dead Orbit, Future War
  Cult, New Monarchy, Cryptarch, Gunsmith, Eris, the Queen, Iron Banner, House of Judgment), the
  Trials of Osiris passage tickets (`pvp_tournament0.*`, `r1_s3`/`r1_s4` tickets), Iron Banner's
  loss tokens, the record books, and every progression a vendor's summary names (the Shipwright's
  racing rank). Every row now has the 56578 client's runtime index, from #322's
  `progression-index.tsv` (117 `character_level` and 118 `character_prestige` were known before
  and agree with it).
- **`vendor-resets.tsv`** (`DestinyVendorDefinition.summary`, 26 vendors). A vendor resets at
  epoch minute *m* when `(m + resetOffsetMinutes) mod resetIntervalMinutes == 0`:
  - daily: 1440 / −540, 09:00 UTC;
  - weekly: 10080 / 2340, Tuesday 09:00 UTC;
  - Xûr (Agent of the Nine): 10080 / −12060, Friday 09:00 UTC.
  The Gunsmith (900) resets on Wednesday at 09:00, and the Shipwright repeats every three days.
- **`refund-policies.tsv`** (`DestinyVendorDefinition.sales[]`, `refundPolicy`/`refundLimit`).
  Only Eververse (67 of 123 sales) and its Silver Dust store (63 of 247) have refundable sales,
  policy 2, **15 minutes**. This matches Bungie's FAQ of 21 October 2015. The table lists the
  refundable item hashes. vendor.rs knows only the client's content index, so for now the rule
  applies per vendor.

`activity-rewards.tsv` is not derived from the manifest. Most completion rewards were server-side
rules that neither the client nor the manifest holds. Every row says where its values come from,
and anything without a source is marked `stand-in`; the store logs that label when the row applies.
A Guardian Rises' 900 XP is a stand-in: it is what the lab's post-game push serves, exactly level 2
on the curve. No community data is used. If values from the Cryptarch Guide archive (GPL-3.0) are
ever added, they must be marked as stand-ins in the same way.

### Refunds

When `D1_STORE=1`, a 901 purchase from Eververse or Silver Dust (vendor hash `0xe97aaa75`, client
vendor 12) writes a refund record that expires 900 units after the 901's stamp. Purchases from
other vendors (Eva, the quartermasters) write none. This assumes the stamp counts seconds, as the
lab's existing 1,800 default did; that is not measured yet. With the store off, every purchase
keeps the 1,800 window, as the lab has run since #167. `D1_REFUND_WINDOW` forces one window for
every vendor in both modes. The 905 refund itself is still decoded only, not applied
(`PlayerStore::take_refund` is ready for it).

## The trait other streams plug into

`player_store::PlayerStore` is implemented by `Store`, on disk (`Store::open`, `open_player`) or in
memory (`Store::in_memory(identity, &Sources::default())`, for tests). Inside the responder,
`player_store::with_store(|s: &mut dyn PlayerStore| …)` lends the live store, and returns `None`
when the store is off. Mutators change the in-memory record only, so the caller then calls
`save_now` (important) or `mark_dirty` (periodic).

| Stream | Methods |
|---|---|
| H (identity) | `identity() -> Identity {account, character, profile}`, `player()`; plus the free functions `identity_for`, `Store::open_player` |
| I (vendors, inventory, bounties) | `items`, `put_item(soid, element)`, `remove_item(soid) -> bool`, `mint_item_soid`, `currency(content)`, `adjust_currency(content, delta) -> Result<u32>` (no debt, no unknown slot), `refunds`, `push_refund`, `take_refund(instance, now)`, `refund_window(vendor_hash, item_hash)`, `bounties`, `put_bounty(Bounty {item_hash, objectives, completed, acquired})`, `remove_bounty`, `roll_vendor_resets(schedules, now)` |
| M (rewards, Light, Grimoire) | `xp`, `add_xp(amount) -> XpGrant` (through the curves into the profile object; marks it stale), `add_reputation(name, amount)`, `reputation(name) -> (progress, rank)`, `light`, `set_light`, `grimoire_score`, `add_grimoire_card(card, score)`, `completions`, `unlock_flags`, `change_unlock_flags(add, clear)` |
| J (checkpoints) | `checkpoint(activity)`, `set_checkpoint(activity, step)`, `clear_checkpoint(activity)` |
| all | `save_now(what)`, `mark_dirty(what)` |

After `add_xp` or `add_reputation`, call `player_store::push_profile(what)`. It re-encodes the
edited profile with the client's codec, saves, and writes `D1_PROFILE_PUSH_FILE` for delivery. If
the responder restarts first, the sign-on re-encodes the profile instead.

### Reputation (6 November)

With `D1_STORE=1`, `add_reputation(name, amount)` writes the progression's progress field at the
curve's exported runtime index (`progression::set_progress`, the same 16-byte entry XP uses) and
marks the object stale, so the next push carries it.

- **The store's total is authoritative.** `Store::sync_reputation` folds it into every adopted
  object. A vendor's profile, or an older payload delivered late, gets the total back; it is never
  counted twice.
- **Undecoded profile.** A grant made before the profile is decoded is kept as a pending delta. When
  an object is adopted, the delta goes on top of whatever reputation that object already holds, so a
  seeded profile's own reputation is kept.
- **Pushes.** The `reputation NAME N` control command pushes at once. Stream I's
  `social_hooks::bridge_progressions` pushes after it hands XP and reputation over; XP that the store
  can't take yet goes back to the side store instead of being dropped. A decoded delivery that needed
  folding pushes the folded profile. Sign-on folds, then re-encodes only if something changed.
- **A completion's reward row.** Its reputation now lands in the completing object, not in the one it
  replaces.
- **Not written.** The entry's daily and weekly fields stay as they are; nothing resets them yet.
- **Not verified.** Whether the client shows the rank from the progress field alone. This is an
  offline result (unit tests); no native run was made.
- **Legacy records.** A record from before this change merges its store-only totals into the
  profile's own value by maximum, not by sum.

To adapt a stream's stub trait, implement it for `dyn PlayerStore` (or wrap a `&mut dyn
PlayerStore`) and drop the stub's own storage. A method the trait lacks belongs in the trait, in
this file, so the record has one schema.

## Knobs

| Knob | Default | Meaning |
|---|---|---|
| `D1_STORE` | unset | `1` turns the store on; anything else leaves it off |
| `D1_STORE_DIR` | `%LOCALAPPDATA%\d1reimagined\player-store` | where the files live (never the repository) |
| `D1_STORE_PLAYER` | `local` | the identity's player name |
| `D1_STORE_SAVE_SECS` | 300 | the periodic save |
| `D1_STORE_CONTROL` | unset | a command file polled each second: `activity N`, `xp N`, `complete N`, `checkpoint N STEP`, `reputation NAME N`, `unlock +N -N`; it is renamed `.taken` |
| `D1_PROGRESSION_CURVES`, `D1_VENDOR_RESETS`, `D1_REFUND_POLICIES`, `D1_ACTIVITY_REWARDS` | the repository's tables | override a table |
| `D1_REFUND_WINDOW` | 1,800 (store off) / the manifest's (store on) | force a refund window for every vendor |

## Tests

- **`cargo test -p d1-responder`: 50 passed, 1 ignored** (the existing ignored one). New tests:
  - XP to level from the curve: 899 → 1, 900 → 2, 346,000 → 40; past 40, XP goes to prestige.
  - Rank thresholds for every curve, at and below each step's running total; Crucible, Cryptarch,
    Trials and Iron Banner checked by value.
  - The reset schedule: Tuesday, daily and Friday 09:00 UTC, and a reset minute is its own last
    reset.
  - Refunds: Eververse only, 900 s with the store on; 1,800 for all with it off.
  - Save and load round trips: the record, attributes, unlocks, reputation, checkpoints, resets
    and loot cards.
  - Crash safety: a half-written `.tmp` leaves the old record; an unreadable record falls back to
    `.prev` and is kept aside; neither readable refuses to start.
  - The periodic save, the `D1_STORE` gate, stable identities, and the whole trait in memory and
    on disk.
- **`python -I tools/ps4_setup/test_progression_tables.py`: 2 passed.** One test checks the script
  on a synthetic manifest; the other checks that the committed tables cite their source and keep
  346,000 and the 15-minute refunds.
