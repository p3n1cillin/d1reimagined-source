# PS4 56578: equipping gear works end to end (31 October – 1 November 2026)

Runs sense80, sense81 and sense84 on the owned 56578 image, served from `main`. Owned inputs and run
output stay outside the repository.

## The empty character screen

In Tower North after A Guardian Rises, the character screen showed a silhouette with every gear slot
empty (sense80), though the Guardian in the world wore gear. The gear in the world comes from the
peer card. The character screen reads the profile, and every profile the mission serves held no gear:
the tutorial profiles hold nothing, and the post-game ones hold only the Arcadia.

## Where gear lives in the profile

The profile (`0x80801743`) decodes to 29,560 bytes:
- 340 inventory slots of 32 bytes from `+0x38`. An instanced item is its u16 content index, its u64
  instance at `+8`, and quantity 0 at `+0x10`.
- **20 equipped item SOIDs (u64) at `+0x2B80`** (`d1-oracle profile layout`; this note first gave
  `+0x2B78` with indices one higher, which addressed the same bytes but left the last entry out).

The geared fixture gives each bucket's index in that array:

| Index | Item | Bucket | Slots |
|---|---|---|---|
| 0 | subclass | `0x06` | 40 |
| 1–5 | the armour | `0x07`–`0x0B` | 43, 53, 63, 73, 83 |
| 6–8 | the weapons | `0x02`–`0x04` | 93, 103, 113 |
| 10 | vehicle | `0x0D` | 143 |
| 11 | ghost | `0x0E` | 153 |

Entries 15 and 16 hold ids that aren't in the inventory; the other entries are empty.

`d1-character-fixup.py profile IN OUT --item SLOT:CONTENT:INSTANCE[@N]` writes such an entry. Any
item named must also be served as a `0x80801732` element (`D1_INVENTORY`). The responder keys those
by file order (`0x301` + index), and each item's own instance must match its key.

## Equipping

- **sense81.** The post-game profiles held the tutorial gear plus the Khvostov, all equipped, and a
  second Khvostov (`0x30B`). The character screen showed the gear. Choosing the second rifle under
  Primary Weapons and pressing ✕ Equip sent the first `inventory_equip_item` (403) seen: request
  `d10000000000030b00`, decoded as `0x80801942` = one u64 instance. The responder answered with the
  result composite (#151), and the session carried on.
- **sense84** (the responder from #153). The equip was applied and pushed:
  ```
  ⭐⭐ EQUIP APPLIED: 0xd10000000000030b (slot 94, bucket 0x2) equipped at index 7, replacing 0xd100000000000401; profile push written
  ⭐⭐ PROFILE PUSH: … as family-4 delta version 6
  ```
  (logged with the old numbering; index 7 there is entry 6 of the array at `+0x2B80`.)
  Equipping the inventory slot again then sent `0xd100000000000401`, the rifle that had been equipped
  before. So after the push the game's inventory held the old rifle in that slot, and the swap went
  back the same way (delta version 8). The client asks, the server applies, the client takes the push,
  and its view follows.
