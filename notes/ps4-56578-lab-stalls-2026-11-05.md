# PS4 56578: the route-run stalls (3-5 November 2026)

Since the evening of 3 November, unattended route runs of A Guardian Rises have stalled. There are three kinds of failure:
- **The client's own gaps:** "N milliseconds since the last network update", 4.7-23.7 s.
- **The game's block detector:** an `Unhandled Exception 0xc000001d` after the ud2.
- **Losing the activity host:** "Lost connection to activity host (last received 20519 ms)", error baboon.

They come with every D1 emulator feature off (`D1_VIDEO=0`, `D1_RATE_RULES=0`, no detours installed). These two runs on 5 November narrow it down.

## cine-live8 (08:59-10:17): clean, with nothing else running

The Codex app was closed at 08:57, at the user's request. Closing only its computer-use helper made the app restart the helper, so the app went.

The run played the whole route unattended:
- from the checkpoint, through the Wall, junction-west, the Divide, Dock 13 and the hangar;
- to the post-game and CONTINUE into activity 165.

The client logged two gaps, 635 ms and 4.9 s, both while loading into orbit. **There was no gap during play.**

## cine-live9 (10:24-11:08): the host stalled while a build ran

About 10:52, Codex started on an offline task (`codex exec`, with its computer-use helper and turn notifier turned off). At 11:03:09-11:03:30 it began building `unicorn-engine-sys` from scratch: cmake, ninja, and the MSVC compiler and linker, at normal priority.

At junction-west, the activity host's log fell silent from 11:03:34.6 to 11:03:51.4 (16.8 s). It didn't even record the client's udt-15 messages, which arrive every 2 s. A gap of about 8 s came just before. The client then logged:

    [PRIVATE CURRENT] Lost connection to activity host (possible crash) (last received 20522 ms > timeout (20000 + 500) ms)

Meanwhile its own network gap was only **212 ms**. The client was fine: **the host stopped sending.** The repair state machine failed and the client went to cleanup.

cine-live5's drop (04:39) has the same signature on the client: "last received 20519 ms".

## What the host's log shows

The connection loop (`listener::drive`) is one task. Each `on_frame` and `on_tick` runs the client's own codec under Unicorn synchronously, and nothing is written meanwhile, heartbeats included.

Silences of 5-9 s show up in the host log even in the clean run (cine-live8: 9.2, 9.2, 8.0, 7.5 s ...), though the host heartbeats every 2 s. So **the host's loop is regularly held for seconds**, and a slow-down from CPU contention can push one past the client's 20.5 s timeout. The sense decoder is not the cause: it runs on its own thread and is fed with `try_send`.

## What to do

- **Don't build or decode at normal priority during a route run.** Start such work at Idle priority (PowerShell `Start-Process`, then `$p.PriorityClass = 'Idle'`; child processes inherit it). For the rest of cine-live9's window, Codex's process tree was set to Idle.
- **`d1-activity-host` now warns when one turn holds the loop for over 1.5 s** ("slow tick/frame: N ms ..."), naming its first event. The next run with a host built from main will say which step it is.
- **Then take that work off the connection task,** so heartbeats keep flowing. One way: a writer task that sends heartbeats on its own timer, with codec work in `spawn_blocking`.

The served host in the lab is the private 2 November build, so it has neither the warning nor any later change.
