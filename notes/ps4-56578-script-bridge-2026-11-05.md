# PS4 56578: the script bridge in the activity host (5 November 2026)

**Result: `d1-activity-host` can now be driven by Destiny's own mission scripts**, through a sidecar
process running Blam Network's MIT BullShcript VM. It keeps a row table and sends udt 5 the way the
live hosts did: the full list at the join, then only the rows that changed, with a heartbeat when idle.
It is **off by default** (`D1_AH_SCRIPTS=1`). Its first lab run (fg2, 6 November) stalled in the load
screen; [the first integrated run](#the-first-integrated-run-6-november) says why and what changed.
Nothing here is claimed in play until a run shows it.

The sidecar itself is Stream A1's ([tools/script-host](../tools/script-host/), [its note](ps4-56578-script-sidecar-2026-11-05.md)). It runs the restored 56578 scripts as a local
input only; they are unlicensed and never enter this repository. This note is the host's half and
the message contract between the two.

## Why

The host was a step machine. Each `D1_AH_MISSION_STEPS` step swapped a whole prebuilt sensor list on
a timeout, an incident, a trigger, a slice or a squad count. A script changes one row at a time (one
squad placed, one cinematic started), so the host needed three things:

- a row model;
- encoders from BullShcript's item states to 56578 row images;
- frames that carry only the changed rows.

The gap analysis of Fukugen Daihon on our host found all three missing. That analysis stays outside
the repository because it names unlicensed paths.

The hooks into the existing host are one field and six short calls in `state.rs`, and two in
`main.rs`. Each is marked `D1_AH_SCRIPTS hook`. Another field in `sense.rs` carries squad state
bytes. An activity the bridge's table does not name is served exactly as before.

The bridge also implements stream G's `public_events::BubbleScriptBridge`. `start_bundles` sends
protocol 1's `active_bundles`. `start_event` and `stop_event` are refused, because protocol 1 has no
message for one event: an event runs from its own bundle's scripts once that bundle is active. The
live public-event chain is in [completion.rs](../ps4/d1-server/crates/d1-activity-host/src/completion.rs)
for G: 415, then 1918, 3077, 732 and 2217 (selector 14), with the event's state in its objective record.

### The udt 5 stream

These rules follow [the stamp and init note](ps4-56578-udt5-stamp-init-2026-11-05.md):

- **The full list comes first, with every row the world's list names, each `fresh`, and the authority
  table.** The walker clears an entry's pending byte only when a frame carries that entry. So deltas
  wait until a full list has gone out. A rejoin or a world re-setup sends the full list again, with the
  rows' current values.
- **Deltas carry each changed row once, with its latest value.** Entries stay `fresh`, as the live
  host's decodable deltas were. The live host's `fresh = 0` partial overlays are not built.
- **A heartbeat goes out 3 s after the last frame**: gen, the stamp, `init = 0`, no entry. These are
  the live idle frames.
- **Rows the world's list does not name are held back**, and the host logs them once. A frame naming
  an entry the client has no sensor client for is untested, and if the client refused it, every row
  in that frame would be lost. `D1_AH_ROWS_UNLISTED=1` sends them anyway.
- **Encoding happens off the connection loop.** A frame that cannot be encoded is planned again
  after 3 s, and heartbeats continue meanwhile.
- **Each lifetime state reaches the client in its own frame.** When the scripts set results and then
  ended in one tick, the second waits until the first has gone out, and `ended` waits for the last.
  The post-game reads the scoreboard while the phase is below 7
  ([post-game note](ps4-56578-postgame-2026-10-29.md)). For a cinematic-only activity the 8 frame
  carries the 6 frame's stamp, because the live hosts sent both in one tick.

### The codec

There is no codec abstraction of the bridge's own. Frames and completion bodies go through the
host's `AhWireCodec`, the trait stream B's `NativeCodec` (#317) implements, via two provided
methods:

- `encode_sensor_entries(&SensorEntryFrame) -> (bytes, stamp_bit)`;
- `encode_object(tag, image) -> (bits, payload)`.

By default both use the client's own codec on `rows_oracle`, so a script tick never queues behind the
host's join encodes; that worker keeps one codec per tag. Under `D1_RSAT_NATIVE=1`, `NativeCodec` builds
them with d1-rsat when every schema is covered, and otherwise falls back as its udt 5 path does.
`CodecWorker` runs the chosen codec on its own thread, because a call to the client's codec waits on
its oracle worker.

### Row encoders, and what the evidence supports

Each encoder writes only the fields that have 56578 evidence. The rest of the image is kept from the
world's served list, or from the client's default. Each script field we cannot place is logged once
as not encoded.

| Kind (type id) | Written | Evidence |
|---|---|---|
| lifetime (16) | state at +0. The mission-phase tuple at +4/+8/+0xC only under `D1_AH_SCRIPTS_MISSION_PHASE=1` | The client's readers and 52 live captures ([wire catalogue](ps4-56578-wire-catalog-2026-11-05.md)). The tuple's layout comes from the descriptor; its meaning comes from TU0 and is unverified ([Fukugen Daihon note](ps4-56578-fukugen-daihon-2026-11-05.md)) |
| cinematic (6) | start +0 (the stamp − 1), change counter +4 (advanced on each start or stop), playing +8 | The `0x403140` setter acts only on a counter change; every live start was stamp − 1 ([cinematic start](ps4-56578-cinematic-start-2026-11-05.md), [live captures](d1-live-captures-2026-11-05.md)) |
| player trigger (29) | enabled +0, the arming +4 (16 bits, kept nonzero while enabled) | Our armed images; the live +4 changes |
| squad (1) | objective ref +0, count +0x2C/+0x30, generation +0x44 = wave + 1. Wave 0 is the client default | The `d1-squad-states.py` layout (proven at generation 2); the live squads' objective ref. Task, temperaments, placedAt and roster are **not encoded** |
| player objective (32) | mode +0 (Incoming → 1 with the NEW MISSION banner, Active → 3 the title, others cleared), nav point +0x60, machine +0x4C | `sensor_objective.rs` (native divide16). Mapping Incoming to 1 is our reading |
| object (4) | incarnation +0, created +8 | The 56578 prop layout ([blockers 15 Oct](ps4-56578-blockers-2026-10-15.md)). Device, interactable and components are **not encoded** |
| scoreboard (15) | player row 0's stats, f32 at +0x20 + 4 × column, in the served image | The post-game draft: kills at column 0 (+0x20), precision at 18, deaths at 22. Columns come from `D1_AH_SCRIPTS_SCOREBOARD_COLUMNS`. Other players, teams, global stats and notifications are **not encoded** |
| timer, sequence, trigger group, object filter, machine, hard-wipe globals, actor and the rest | nothing (`Unsupported`); the row keeps its served value | No 56578 field map yet |

The lifetime mapping from BullShcript's runtime states. The live order is 0 → 1 → 3, with 4 around
each cinematic; the ending depends on the activity's kind (`kind=cinematic` in the activity table):

| Runtime state | 56578 value | Notes |
|---|---|---|
| pregame (0) | 1 | about 20 s after 0 |
| countdown (1) | 2 | never served in PvE |
| active (2) | 3 | the spawn gate accepts it |
| cinematic hold (3) | 4 | |
| results (5) | 6 | the completion tick |
| ended (6), gameplay | **7** | 30–31 s after 6 in 36 of 39 live activities, which is the scripts' `end_game(30)`. 7 opens the post-game screens and freezes the scoreboard |
| ended (6), cinematic-only | **8** | 6 and 8 in one tick, no 7. 8 is the client's own end-of-activity transition |

Runtime state 4 has no name and is not sent; 56578's 5 and 9 are never served in PvE (the client
treats 9 like 7). The sidecar's `wire.phase` always ends on 8; where it disagrees, the host's
mapping stands, and the disagreement is logged once.

### Incidents, senses and completion

**Client incidents** (udt 18) are translated through the catalogue:

| Incident | Sent to the sidecar as |
|---|---|
| 3403 | `trigger`, with the row its body names |
| 891 / 1726 | `cinematic_finished` / `cinematic_skipped`. The row is the one named at bit 303 as 3403 names its trigger (unverified for these ids), else the one cinematic playing. When two cinematics are playing, the incident is dropped rather than guessed |
| 566 / 2014 | `player_spawned` |
| 2079 | `player_died` |
| anything else | `incident {id, name_hash}` |

An id outside the catalogue is dropped and logged. The catalogue is checked at load against the nine
identities the bridge acts on, and a table that disagrees is refused.

**Senses** (udt 6, `D1_AH_SENSE_SCHEMAS`):

- A squad's live-member count (B +0x0C, proven by the member-death control) goes out as
  `squad_alive`.
- Its state byte +0x19 and bit +0x1A are decoded when they change, and logged. These were traced
  statically from the squad record's flags ([sensor sense](ps4-sensor-sense.md)); what they mean in
  play is not established, and protocol 1 has no message for them.
- Objective counts, object alive and health have no evidence yet and are not decoded.

**`activity_complete`** sends one udt 18 the way all 55 live completions did
([wire catalogue](ps4-56578-wire-catalog-2026-11-05.md), "The complete encoding of incident 965"):

- **The incidents:** 965, 3235, 2937, 2009 and 614 (all selector 27); a cinematic-only activity
  leaves out 3235.
- **One body,** `0x80800595`: a 128-byte struct, 725 bits on 56578, encoded through the host's
  codec. Its fields:
  - the instance word and this host's id;
  - the completing player (the first qword of its identity);
  - the activity's bundle hash, its two type hashes, the empty hash and its place hash;
  - the constants every live body has;
  - the counters.
- **The hashes** come from the activity's manifest definition, given in the activity table (`hash=`,
  `type=`, `type2=`, `place=`), never from a captured body. Without them the completion is not sent,
  and the log names the gap.
- **Stand-ins, labelled in the code:**
  - the counters: the four live 51539 values, `0, 0, 1, 1` or `0, 0, -1, -1`, fill four of 56578's
    seven slots, and which slots they belong in is open;
  - the session id at +0x30 is 0;
  - the instance word is the host id's low half.

**`ended`** calls `ActivityRewards::grant_activity_rewards` once for each character that joined:

- the outcome is `Completed` if the scripts completed the activity, else `EndedIncomplete`;
- it is `Abandoned` if the sidecar stopped first.

A character is the client's own 40-byte `join_request` identity; the host never learns a character
id. Stream M's service ([rewards and growth](ps4-56578-rewards-and-growth-2026-11-05.md)) lives in
d1-responder, another process: `rewards::grant_activity_rewards(&mut store, CharacterId,
activity_hash, &ActivityOutcome)`. The host-side trait is the seam for an adapter that maps the
identity to a `CharacterId` and forwards the call, with `Completed` as `completed: true`. **One
difference to settle:** M's note says to call it at `activity_complete`, while the bridge calls it
when the lifetime ends. The Fukugen Daihon note asks for profile completion to stay separate from
the pre-outro notification, and the harness also waits for the end, so the next activity does not
launch while the outro plays. The bridge follows that until the owner decides otherwise.

**Update (stream K, same day):** decided: the bridge now grants at lifetime 6, the results, so the post-game at 7 shows the rewards, and one `ActivityRewards` trait serves the bridge and the open world. The slice tables, the content export and the remaining field maps are done too: see [every story mission from its own scripts and content](ps4-56578-story-missions-2026-11-05.md).

**`phase`** asks for the host teleport when the client is not in the phase's region. Protocol 1 names
the phase's slice by name and hash, not by its slice-set id, so the region comes from the activity
line's `regions=PHASE:REGION,...` until content resolves it. The teleport reuses the mission step's
region path: the start region, the PAH token and the slice request.

### Supervision

- The host spawns one sidecar per instance at the join of a scripted activity.
- stdin, stdout and stderr each have their own thread, so a slow sidecar never blocks the
  connection loop. The child is killed on drop.
- A sidecar that does not start is tried three times, 2 s apart.
- One that exits after `start`, or answers with a fatal `error`, halts progression (no ticks, no
  events). The rows already sent stay and heartbeats continue, so the client is not dropped. Nothing
  is guessed in the sidecar's place.
- **Stand-in rows never reach the wire.** When `loaded.stand_in` is set (no content export), the
  sidecar's row indices are its own, not the game's. Only the lifetime, which the bridge keys from the
  world's list, is sent.

## The first integrated run (6 November)

Two lab runs on the full-game profile (`ps4/profiles/full-game.env`), with a tutorial Guardian and
`D1_AH_ACTIVITY_REMAP=164:165`, so A Guardian Rises launches the reveal cinematic (165, `cine_reveal`).

- **fg2, bridge on (`D1_AH_SCRIPTS=1`): stuck.** The client stayed in
  `activity:initial_slice_set_loading`, a black load screen, for more than 11 minutes. It never
  reported 2681 and never reached `in_world`. Within 12 s of the join the host:
  1. sent the bridge's own 22-row init list, at lifetime **3**;
  2. started the scripts as soon as they loaded. Phase 0 `cine_106_trv_phase` asked for region 25,
     and the host sent a teleport to 25;
  3. moved the lifetime **3 → 1** (pregame), then **1 → 4** (the cinematic hold).

  The client's log shows what the teleport did. Its initial slice set was already `PRV25.25`. The
  teleport began a second transition to 25, de-instantiated the CURRENT slice set, and the load never
  finished. The client never sent a udt 6 sense either.
- **fg3b, bridge off, step schedule `cine-reveal-steps.txt`: plays.**
  1. Step 0 at +0 s served the world's live list (`sensor-clients-cine_reveal-live.txt`: 21 sensor
     clients, `@phase 0`). The client answered with a udt 6 sense 0.2 s later.
  2. Pregame (lifetime 1) came at +61 s and the hold with /6/0 playing (lifetime 4) at +62 s.
  3. The client reported 2681 at +63 s, still loading, then 891 at +95 s, then reached `in_world`.
  4. No teleport came before the first cinematic had finished.

**Root causes, all four fixed in the bridge.**

1. **The first lifetime was the launch phase.** The generated list (`@generated start=25`) names no
   `@phase`, so `params_for_list` fell back to `D1_AH_SENSOR_PHASE`. lab-base sets that to 3 because
   the knob arms the whole sensor path. Showing 3 and then 1 is a step backwards. Every live mission
   starts at 0 ([wire catalogue](ps4-56578-wire-catalog-2026-11-05.md): 0 → 1 → 4 → 6 → 8 for the
   reveal). **Now** the bridge starts at the list's own `@phase`, else 0
   (`ScriptedActivity::initial_lifetime`). Stream R's Crucible worlds keep `lifetime_state`.
2. **The first list was not the world's.** The generated list has the same 21 records as the live
   one, but no values. It lacked /6/0's idle cinematic value and the player bundle's spawn value
   (`0x808022A5`, team -1), and its lifetime was 3. **Now** a scripted activity that
   `D1_AH_WORLD_TABLE` names starts from that row's list, as the world table and step 0 serve it.
   Every record keeps its value. The bridge's own rows are merged in: a row only the bridge names
   is kept, and a row both name takes the world's value, or the bridge's where the world gives none.
   The world list's `@phase` and `@authority` win when it names them
   (`ScriptedActivity::merge_world_list`, `apply_world_table`). The slice lists stay the generated
   ones; moving to a slice set relists, and the values the table holds are kept. For 165 the first
   full list is the 21 live records with their values, plus the lifetime at 0.
3. **The scripts started during the initial load.** No real "client loaded" signal reaches the host,
   so none could be used. These were checked in both runs:
   - udt 21: no slice-set report until after the teleport. fg3b's `%26` gate timed out.
   - udt 36: answers only membership updates.
   - udt 47 `high_water`: a 60 s beacon.
   - udt 6: answers the first frame, not the load.
   - The sidecar's `player_spawned`: the spawn gate rejects lifetimes 0, 1 and 4, so in a cinematic
     the player never spawns first.

   **Now** `start` waits **`D1_AH_SCRIPTS_START_DELAY`** after the first full list. That is 60 s by
   default, a **stand-in** copied from the working schedule's cushion. Until then the bridge sends
   `hello`, the world's list at lifetime 0, and heartbeats. `players` goes with `start`, and client
   incidents in the cushion wait and follow the start in order. The bridge never sends
   `player_joined`.
4. **The teleport during the initial load.** The world's start slice set is 25 (the hand table, the
   generated `start=25`, the client's `PRV25.25`), and phase 0 runs in 25. **Now** the bridge tracks
   where the client is: its udt 21 report, else the last region the host moved it to, else the start
   slice set the instance serves (`set_served_start`, from the membership's region record). A phase
   there asks for no move. The instance also refuses a script teleport to its start region until the
   client has reported a slice set (`state.rs`, `script_teleport`).

- **Arrival.** The client is taken to have arrived when it reports the slice set (udt 21), else when

## The message contract

The contract is A1's [tools/script-host/PROTOCOL.md](../tools/script-host/PROTOCOL.md), protocol 1;
the bridge follows it. In short:

- **The handshake.** `hello` is answered by `loaded`. `start` goes once the world's full list is out,
  and is answered by `ready`.
- **The clock.** The host owns it: one `tick` per udt 5 stamp step (10 Hz), carrying the stamp, so a
  row's recorded time is the stamp its frame goes out near. Polls are coarser than 100 ms, so each poll
  sends every step since the last. A sidecar 200 ticks behind holds the clock rather than being flooded.
- **Rows.** Host messages name a row by `bundle` and `type_index`. The sidecar's rows are BullShcript's
  `ItemChange`, and lifetime changes add `wire.phase`, which the bridge checks against its own mapping.
- **What the bridge does not send yet:** `active_bundles` (it needs the slice → bundle table from
  content) and the sense messages marked "later" there.

## Knobs

| Knob | Meaning |
|---|---|
| `D1_AH_SCRIPTS=1` | Turns the bridge on. Default off. |
| `D1_AH_SCRIPTS_SIDECAR` | The sidecar command, split on whitespace: `node tools/script-host/src/sidecar.mjs`. The sidecar reads `D1_SCRIPTS_DIR` and `D1_TIGER_DIR` from the environment. |
| `D1_AH_SCRIPTS_ACTIVITIES` | The activity table. One line per activity: `INDEX ACTIVITY GROUP LIST [hash=H] [kind=cinematic] [type=H type2=H place=H] [bundles=PATH] [map=B:G,...] [regions=P:R,...] [team=0]`. LIST is a sensor-client list, read relative to the table as world tables are; its `@authority` and `@phase` apply. `kind=cinematic` ends on 8 and leaves 3235 out of the completion; the four hashes (all or none) make the completion body. |
| `D1_AH_SCRIPTS_INCIDENTS` | The catalogue TSV. Default `ps4/fixtures/56578/incidents-56578.tsv` (#306); the 51539 map beside it is read when present. The path is also passed to the sidecar. |
| `D1_RSAT_NATIVE=1` | Stream B's knob: frames and bodies go native where d1-rsat covers them. |
| `D1_AH_SCRIPTS_MISSION_PHASE=1` | Write the mission-phase tuple into the lifetime. |
| `D1_AH_SCRIPTS_SCOREBOARD_COLUMNS` | A file of player stat column hashes, one per line, in column order. |
| `D1_AH_ROWS_UNLISTED=1` | Send rows the world's list does not name. |
| `D1_AH_ROWS_DELTA_INIT=1` | Set `init` on deltas too. Harmless to the client; a fallback in case the latch is ever cleared unseen. |
| `D1_AH_SCRIPTS_SLICE_LISTS` | A `D1_AH_MISSION_STEPS`-format file (default: `D1_AH_MISSION_STEPS`). Its first step and its region steps give the served values of the records a slice set adds: the base image of a script change, and the full list's value until the scripts set one. The full-game profile names `cine-reveal-steps.txt`. |
| `D1_AH_SCRIPTS_ARRIVAL_CUSHION` | Seconds the script clock stays held after the client is taken to have arrived in a slice set a phase moved it to (its udt 21 report, else the host's teleport request dropped, else 120 s). Default 20, a **stand-in**. |
| `D1_AH_SCRIPTS_START_DELAY` | Seconds from the first full list to the scripts' `start` (and `players`). Default 60, a **stand-in** cushion while the client loads its initial slice set; `0` starts as soon as the list is out. |
| `D1_AH_WORLD_TABLE` | (lab-base's hand world table) A scripted activity it names starts from that row's list, with its values and `@phase`, and the bridge's own rows merged in. |

## Tests

`cargo test -p d1-activity-host -p d1-oracle`. The tests cover:

- **Deltas:** the full list first with init and authority; deltas only after it, each row once at its
  latest value; failed frames planned again; rejoin and reload; unlisted rows held; resets.
- **Heartbeat timing:** none before the first frame, then one at 3 s, with a delta resetting the timer.
  The 10 Hz stamps are checked against the live host's 75 / 105 frames.
- **Phase mapping:** the runtime → 56578 lifetime table, and the lifetime image staying byte-identical
  to the audited one until a mission phase is given.
- **Encoders:** per kind. Kinds with no 56578 field map are refused, not guessed.
- **The protocol:** host messages serialise to protocol 1's lines; the sidecar's `loaded`, `rows`
  (with `wire`), `phase`, `activity_complete`, fatal `error` and `tick_done` parse.
- **A fake sidecar,** a Rust test double speaking protocol 1, drives a whole synthetic two-cinematic
  activity:
  - join, full list, `loaded`, start and pregame;
  - one tick per stamp step, none skipped;
  - the first cinematic at the hold, then heartbeats;
  - 891 naming its row, and a phase that moves to region 26;
  - `activity_complete`: one udt 18 with 965, 2937, 2009 and 614 and one body carrying the table's
    hashes, this host and the player;
  - the second cinematic, attributed by elimination;
  - results and ended in separate frames, 0 → 1 → 4 → 6 → 8, with 6 and 8 on one stamp;
  - rewards once; no ticks after the end;
  - every frame stamped, with stamps nondecreasing.
- **The reveal as the profile serves it** (the committed fixtures: stream K's table, the generated
  worlds and slice states, lab-base's hand world table, `D1_AH_SENSOR_PHASE=3`):
  - the first full list is the live list's 21 records with their values, at lifetime 0, never 3;
  - for the 60 s cushion there are only heartbeats: no phase, no lifetime past 0, no teleport, and
    nothing to the sidecar but `hello`;
  - an incident in the cushion follows `start`;
  - then 1 and 4, no teleport for phase 0 (region 25, the start), a teleport to 26 for phase 1;
  - the live order 0 → 1 → 4 → 6 → 8.
- **The merge:** the world's records first, in its order, then the rows only the bridge names. The
  world's values win. A table row for another world, group or lifetime record is not used.
- **The instance:** a script teleport to its start region is refused until the client reports a
  slice set; another region is sent.
- **The list follows the slice set (fg2c):**
  - slice set 26's list is `cine_reveal-move-26.txt` record for record;
  - phase 1's move sends it in full with no udt 21 report, /6/1 idle and listed;
  - the Tower cinematic's play is a delta, nothing is held back;
  - then 6, the grant through the forwarder (a `grant` line in the store's command file), 8 on 6's
    stamp, and the `handoff` line to activity 0.
- **The hold after a move (fg2e):**
  - no ticks and no Tower play while the client moves or in the cushion;
  - the arrival (the teleport finished, or a udt 21 report) resends the slice set's full list;
  - another region's teleport is not this arrival;
  - the timeout releases a move no arrival was seen for.
- **Served values (fg2d):**
  - only the move-26 list adds a value, /6/1's;
  - /6/1 idle in the move's full list is `cine_reveal-move-26.txt`'s byte for byte;
  - its play is `cine_reveal-play-1.txt`'s byte for byte but the start;
  - without the slice lists /6/1 has no served value.
- **A gameplay ending:** 6 then 7, and all five incidents with completion counters.
- **Stand-ins:** only the lifetime reaches the wire.
- **Stream G's seam:** `start_bundles` sends `active_bundles` once the scripts run; one-event calls are
  refused.
- **The completion module:** the body's layout and the envelope's. With the eboot, the body is 725
  bits through the client's codec.
- **Failure paths:**
  - a sidecar that dies after `start` halts progression, but heartbeats continue and the outcome is
    `Abandoned`;
  - a sidecar that never starts is tried three times;
  - a completion with no manifest hashes is not sent.
- **The real catalogue,** committed by #306: 3,902 records, and the 789 → 965 and 734 → 891 joins.
- **The oracle:** `SensorFrameEncoder` is byte-identical to the one-shot encode across three frames,
  using the client's real codec.
