# PS4 56578 wire catalogue (5 November 2026)

This catalogue separates executable type facts, content routing and field meaning. It targets
**CUSA00219, build 56578.17.04.12.1251.evil, package 01.33**, executable SHA-256
`672f03411c0503dfbcda804cbb9fb27cdd9a8d73a8bcb71bf0c4f688073b0833`.
All work here was offline: static extraction, read-only Ghidra 12.2 decompilation and synthetic
Unicorn codec tests. No emulator or game was launched. Addresses below belong to this executable.

The reproducible [generated tables](../ps4/fixtures/56578/rtti/README.md) contain **2,633 classes,
2,430 vtables, 22,920 virtual slots, 4,566 RSAT schemas, 6,861 field slots, 1,690 instance-checksum
records, 63 BAP envelope classes and 101 investment service definitions**. Additionally,
19 protobuf roots expose 141 distinct descriptor fields. One RSAT schema, `0x80802049`, has a
missing marker; it is explicitly incomplete. These totals measure extraction, not semantic decoding.

`tools/ps4_setup/d1_rtti.py` delegates to the existing Rust ELF/relocation/RTTI/RSAT readers and
the existing Python protobuf descriptor reader. It does not implement another codec. The investment
definitions came from the owned 56578 content tag `0x80a5e37a`, read with the local MIT Gibbon reader:
101 records, stride `0x40`, with the existing Rust definition parser checking the layout. Only
names, IDs, addresses and layouts were exported; the private table's digest is in the manifest.

**Status vocabulary:** **D** = already decoded/modelled in this repository; **N** = newly recovered
layout or code-to-service link here; **U** = unresolved semantics, routing or runtime setup.
An N layout does not imply that its business rules have been implemented. Anonymous `fN` names
are field positions, not recovered Bungie names. The tables retain the actual kind/parameter words.

## Reading the IDs and fields

- Investment IDs such as 903 and 905 ride inside **BAP 10**
  `c_investment_bap_message_client_to_world_server_request`; replies use **BAP 11**
  `c_investment_bap_message_client_to_world_server_response`. The investment ID stays the same.
  Their argument structs are identified by RSAT tags. RTTI does not supply original C++ names for
  most of these value structs; their class identity below is `RSAT[tag]`.
- BAP IDs 36–43 name actual RTTI message classes. Their bodies are protobuf, not RSAT.
- QueueZ **BAP 123** pushes families and instance checksums. A checksum is not necessarily its
  RSAT tag. `instances.tsv` is not a family/type routing map.
- AH udt IDs, sensor kind IDs and incident content indices are three more independent spaces.
  Incident **965 is not a BAP or AH message type**.

`@N` denotes a decoded C byte offset; `?` means a presence bit. For ordinary RSAT structs, kind
low bytes `2/3/4/5/6/7/8/9/0xa/0xb` select bool, biased 8/16/32-bit integer, 64-bit integer,
raw 8/16/32/64-bit integer and float codecs respectively. Signedness in server storage sometimes
differs from the codec's biased interpretation: use the exported parameters. The kind high byte
is presence width. Array headers supply capacity and strides; **an array field's printed offset
can be its stride**. Leaf raw width zero does not mean a boolean or float occupies zero wire bits.

`R` below is shared result `0x80801796`, 8 decoded bytes:
`status:i8/4-bit @0, value:i32/32-bit @4` (bias 1 for status, `0x80000000` for value), **36 bits**.
`I` is item selector `0x80801983`, 24 decoded bytes:
`f0:bool @0, instance:u64 @8, index:i16 @0x10`, **81 bits**.
The index is not a content hash. The selector flag's complete meaning remains U.

### The complete encoding of incident 965 (decoded)

**Envelope (D):** AH udt **18**, `0x8080097d`, 716 decoded bytes: `u32 count @0` and up to 25 biased
12-bit incident indices from +4; a nested raw-u32 list `0x808046b4 @0x68` (empty in every live
completion); and **one metadata body**: `u32 length @0xd4`, up to 500 bytes from +0xd8.

**How the client reads the body (D):** the udt-18 receive handler `0x1018f90` decodes the envelope
and calls the game interface (`0x240940`), which reaches `0xbb2170` → converter `0x2554b0`. The
converter looks up the **first** listed incident's catalogue row (`0x259bf0`), takes its body
selector (row +0x18), and gets that selector's metadata handler (`0x24efd0`: the incident service's
override, else table `0x190aaf0[selector]`). If the handler has no specialization (its slot 0 returns
null) the handler's slot 3 names the RSAT type; otherwise the specialization chooses it. With a
nonzero length the bytes decode as that type (`0x255a50` → `0x2ca150`, a 500-byte read window), and
then the queue command `0x19` carries the incident. **One body serves every incident in the list.**

**The 965 body type is `0x80800595` (D).** Selector 27's handler is the static object
`0x2651de0`, constructed in `0x24f5e0` with vptr `0x190a240`
(`c_activity_complete_incident_metadata_interface`) and subobjects `0x190a1c0` (its Xetrov definition)
and `0x190a200` (its investment interface). Its slot 0 is `0x1df0` (returns 0: no specialization);
slot 3 `0x10150b0` reads the type cell `0x26aae60` through pointer slot `0x191af58`. The type-cell
table entry at `0x192a5a0` pairs that cell with FNV name hash **`0x567b4fb2`**, and the only RSAT
descriptor carrying that hash is `0x80800595` (hash at descriptor +8, `0x1375208`). The hash occurs
exactly twice in the executable. This replaces the earlier structural candidate with a binding.

**Which incidents (D, live):** every one of the **55** live completions sends one udt 18 with five
incidents, all body selector 27, in this order (51539 → 56578 by the
[name-hash join](ps4-56578-incident-catalog-2026-11-05.md)):

Where both are visible in a capture, the chain is sent in the same tick as the lifetime's 6
(gameplay) or its 4 (cinematic-only: completion goes out before the cinematic plays, then 6 and 8

**The body, field by field (D for layout and live shape; names partly U).** No field has a presence
bit, so every body is the same length: **725 bits (91 bytes) on 56578**. Live 51539 bodies are
79 bytes: the same layout with **four** investment counters instead of seven (629 bits); the 56578
codec under-reads such a body, and the new oracle test asserts both lengths.

### Scoreboard (kind 15)

**D carrier; N complete exported rows:** sensor kind **15**, value `0x808008d0`,
19,792 decoded bytes, over AH udt 5. The named RTTI system is `c_activity_scoreboard_game_system`,
typeinfo `0x1906a50`, vptr `0x1906a20`. The six optional root fields are:

| Offset | Type / layout |
|---|---|
| 0 | `0x8080410c`: i32/5-bit count + 16 player rows, stride 1,184 (`0x808006e0`) |
| `0x4a10` | `0x808002e4`: i32/4-bit count + 12 team rows, stride 56 (`0x808008a2`) |
| `0x4cb4` | `0x80804234`: i32/5-bit count + 24 optional f32 values |
| `0x4d18` | `0x808042d5`: i32/2-bit count + 2 rows, stride 16 (`0x8080099a`) |
| `0x4d3c` | raw u32 |
| `0x4d40` | `0x8080055b`: i32 @0, raw u64? @8 |

Player row: optional typed identity @0, bool @8, optional counted stat block @0xc (64 optional
f32 slots), optional counted rewards block @0x110 (4 typed-value slots, stride 224). An inventory
reward needs `0x80801732` registered as a dynamic value type; that is already supported by
`sensor::TYPED_VALUE_TYPES`. Team row: optional i8/6-bit team @0, bool @1, optional counted block
@4 of 12 optional f32 stats. The two 16-byte rows contain optional raw u32 @0, typed identity @4,
i8/6-bit @0xc.

**Per-mode semantics (partial).** The client does not hard-code a mode's columns: the copy into
the UI store (`0x3ff9b0`, frozen once the lifetime reaches 7, 8 or 9) is generic, and the stat
columns are named by the activity mode's scoreboard definition in content (the post-game note's
config `0x80aa3ee6`: kills at 0, precision kills at 18, deaths at 22). Two client consumers fix
meanings that do not depend on the mode: the results data at lifetime 6 (`0xab9b80`) reads the
winning team, its score and the team rows, and the rematch check at 8 (`0x75e600`) compares each
team's score with the leader's against a content threshold scaled by a skill factor
(`blowout score delta`). Per-mode scoring rules, limits and tie-breaks are content (stream J,
`pvp.rs` stand-ins); the 52 captures contain no Crucible match, so no live per-mode row was read.

### Public events (partial: state route found, deltas not decoded)

**Incidents (D):** the live public event in The Dark Within used a separate activity host and the
incidents `public_event_engaged` (51539 342 → 56578 **415**), then `public_event_complete` (**1918**),
`event_completion_reward3` (**3077**), `public_event_complete_gold_tier` (**732**) and `0x919ff2f2`
(**2217**) in one udt 18. All are body selector **14**, whose handler slot (`0x190aaf0[14]`) is the
shared default `0x190aae8`; the public-event metadata class (`c_public_event_incident_metadata_interface`,
vptr `0x190ba10`) must come from the incident service's override and remains **U**.

**State rows (N):** no dedicated public-event sensor root exists. On the event's host, the event's
content group carries an **objective record (sensor kind `0x20`, value `0x80802a1b`, sub 22)** whose
deltas change exactly at the engage (≈209 s) and completion (≈478 s) incidents, beside kind 1, 2, 4
and 5 rows of the same group. Public-event progress therefore rides the existing objective handover
(`sensor_objective.rs`); patrol worlds also carry per-event lifetime records (kind `0x10`, subs 203
and 205 in the patrol content group). The replicated deltas decode only against their previous
image, which `sensor decode-values` does not seed yet, so the per-field progress/timer meanings are
**U**. **Unblocks:** stream H and the patrol host (route events through the objective and lifetime
records, not a new root); stream M (event rewards follow the incident chain).

### Infusion (decoded client rules; the server's mutation is partial)

`cui::c_talent_activation_request` slot 3 `0xa43860` switches on its kind (+0xa9):

| Kind | Validation | Service |
|---:|---|---|
| 1 | `0x284e10(item, node, flags 0)` | **801** `{item, node}` |
| 2 | `0x286130(item, node)` (a node-step check: step counts, required levels, costs) | **802** `{item, node}` |
| 3 | resolve the second item, then `0x26f260(source, target)`; `0x284e10(item, node, ok << 3)` | **804** `{target, node, source}` |

**804 is infusion.** `0x26f260` returns a mask that is 0 when the source item may be infused into
the target: `0x1000` an instance missing, `0x800` a definition missing, `0x100` the source is not
in a bucket of the target's type (`0x26be90`, definition +0x88), `0x400` the target has no infusion
category and `0x40` the two categories differ (definition block +0x30, field +0x4c), bit 0 a state
bit of the source (the lock bit, by the 406 pairing), `0x80` the source is equipped
(`0x2696b0`), and `0x200` no gain. The gain (`0x26f400`) is the two items' attack values
(instance stat plus the level curve) compared: when the source is higher,
`gain = min(diff, max(diff × rate, floor))` with `rate` and `floor` from a per-bucket content
table (manager slot `+0x428`, keyed by definition +0x8a); a gain of at most `0.0001` refuses.
The owned-content export corrected the selector's description: `+0x8a` is the tier category;
inventory buckets use `+0x88`. `items/infusion.tsv` retains all seven rate/floor-index rows.
The floor is sampled on the Attack quality curve, rather than used as a literal number
([rewards content pass](ps4-56578-rewards-and-growth-2026-11-05.md#evidence-needed-by-rule)).
The server's resulting change (the target's new value, the source's removal) is **partial**:
it should apply the same formula with the content rates, but no reply or push was observed.
**Unblocks stream M** (infusion in the growth services) and stream I (the vault/inventory
consequences).

**801 and 802** were sent live (4 and 6 times): node activation and node-step change. **803** has
no static sender.

### Presence blobs (partial)

The friends presence blob is `0x15c3770`, one protobuf `bytes` field of 520 bytes (capacity 512),
used in both the friends update request (BAP 36 f4) and each contact row (BAP 37). The client
keeps per-friend presence buffers in the `Networking Friends Presence Information` heap
(`0x2b24e0`: four tables of 2,000 entries of a configured size), filled by
`c_investment_social_presence_game_system` and the `investment_presence_manager`. The blob's
contents are written by the client and only relayed by the server, and the 360 captures
carry no BAP 36/37 (Xbox Live handled presence), so its fields stay **U**. A server can
store and forward the client's bytes unchanged. The matchmaking advertisement (BAP 42) dump at
`0xae9200` prints game in progress, big party, reputation, social id, bubble id and version: those
are matchmaking settings, not the friends blob. **Unblocks stream H** (relay; no decode needed).

## Validation and next boundaries

The owned-input tests in `d1-oracle/tests/wire_catalog.rs` cover 21 oracle-decoded request/reply roots:
seven inventory/talent requests, five result replies, refund/interact requests plus refund reply,
second-item talent activation and the two Record Book operations with their replies. A further
descriptor assertion checks the empty offers request. Its oracle registry-object binding is
ambiguous, so a full request oracle round trip is not claimed.
Synthetic values exercise actual fields, signed errors, bit counts and changed-value controls;
these tests do not prove transaction business rules or content-to-service routing by themselves.
Without `D1_EBOOT` they print an explicit skip. The Python test verifies the committed table hashes,
hierarchy and field counts, then regenerates every executable-derived table when the input exists.

The existing MIT RSAT cross-check was re-run: **26 OK, 2 DIFF**, the documented unsigned-u32 decode
and default QueueZ version differences. See [the cross-check note](rsat-blam-crosscheck.md) and
[investment-services.md](investment-services.md). Older PS3/01.29 mappings were used as comparison
targets; the 101 service pairs and all addresses above were read again for 56578.

Checks run for this change:

- `python3 -m unittest discover -s tests -p test_rtti_catalog.py -v`: three checks pass with
  `D1_EBOOT`; without it, two pass and the private regeneration check explicitly skips.
- `cargo test -p d1-oracle --test wire_catalog -- --nocapture`: all four test cases pass across
  the full run and the focused rerun of refund/interact after separating the unsupported empty
  offers binding. Coverage is 21 decoded roots, plus the empty descriptor assertion.
- `cargo test -p d1-eboot -- --nocapture`: eight unit tests execute successfully; 33 existing
  reference-build controls explicitly skip because the separate 01.29 input is absent. The new
  Python regeneration and oracle checks above do execute against 56578.
- `rustfmt --check` reports existing formatting drift across the large pre-existing eboot files;
  the new integration test is formatted, and the new CLI block follows rustfmt output.

Builds used two jobs at BelowNormal priority. The full server workspace was not built for this
static-tool change. No native-run verification is inferred from these tests.

Checks added by the open-items pass (no game, emulator or lab run):

- `cargo test -p d1-oracle --test wire_catalog activity_complete`: the client's own encoder writes
  a synthetic `0x80800595` body in **725 bits** for two counter sets, the decode returns every
  field, a changed counter changes the payload, and a 79-byte (51539-length) body is refused as
  under-length. Without `D1_EBOOT` the test skips.
- `python -m unittest discover -s tests -p test_srcp.py`: eight synthetic tests, including the
  incident body length at +0xd4 and the lifetime change filter.
- Private, not committed: `d1-srcp.py lifetime` over the 52 captures (the lifetime table above),
  the 55 completion envelopes decoded with `activity-host decode-batch` and parsed against the
  `0x80800595` layout (every body ends on its padding bits), and the public-event deltas of The
  Dark Within. Ghidra decompiles were read with `d1-ghidra.ps1` against the read-only project.

The remaining blockers, after the open-items pass: the server's infusion mutation; every vendor
selector and receipt field; the Postmaster's choice between 601 and 405; card/book/objective
definition mappings; presence blob fields (relayed, not decoded) and party transitions; lifetime
values 2, 5 and 9; the names of four completion incidents and seven counters; mode-specific
scoreboard rules (content); and decoding public-event objective deltas.
`0x80802049` is also structurally incomplete. The export makes these gaps searchable; it does not
turn unbound RTTI names or anonymous fields into implemented services.
