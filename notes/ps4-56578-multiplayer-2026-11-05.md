# PS4 56578: multiplayer infrastructure on one local server (5 November 2026)

Several independently connected players on one server: identities, fireteams and invites, matchmaking into activities and public bubbles, several clients in one activity instance, and the platform sessions the client uses for its peer-to-peer game sessions.

**Offline only.** Everything here is built and unit-tested with fake in-process clients. No lab run, emulator run or game run has exercised it. Every hook is off by default. With the knobs unset, the servers answer exactly as before.

## Where it lives

| Piece | Code | Knob |
|---|---|---|
| Identities, fireteams, matchmaking directory, playlist and public placement, PSN Session WebAPI store | new crate `ps4/d1-server/crates/d1-mp` (pure state machines; time passed in as ms) | – |
| 42/43 session fields: search params, advertisements, deletes, search results, configuration trees | `d1-bap/src/matchmaking_sessions.rs` (beside the existing 42/43 codec) | – |
| Several clients in one activity instance | `d1-activity-host/src/group.rs`; hooks in `state.rs` and `listener.rs` marked `MP(H)` | `D1_AH_SHARED_INSTANCES=1` |
| Responder wiring (BAP 23, 42/43, WebAPI sessions, sign-off on close) | `d1-responder/src/mp.rs`; one-line hooks in `main.rs` marked `MP(H)` | `D1_MP=1` |
| Matchmaking configurations served for kind 4 | `ps4/fixtures/56578/matchmaking/configurations.json` | `D1_MM_CONFIG_FILE` |

There are three more knobs: `D1_MP_ACCOUNTS` (`<online id>=<soid>,...`), `D1_MP_FIRETEAM_CAP` (default 3) and `D1_MP_RECONNECT_GRACE_MS` (default 120000).

## What the live captures show about matchmaking

These come from the 52 private Xbox 360 captures (build 51539): 1,011 message-42/43 exchanges. Only shapes and numbers were read. No session, name, token or address was copied. `tools/ps4_setup/d1-srcp.py matchmaking CAPTURE...` prints the shapes with ids, hashes, strings and bytes redacted.

- **Matchmaking is client-driven over a directory.**
  - A client that hosts a session advertises it (kind 2) and gets an id back. Its updates repeat the id, and it deletes the advertisement (kind 3) when it leaves. The delete is acknowledged with an empty `f5` (`2a 00`).
  - A client looking for a session searches (kind 1) about every 5 s. Every answer carried at most one candidate: the advertiser's session and name, verbatim, and two scores.
- **Slots and keys.** `f4` is the slot: 0 for the activity, 1 for a public bubble. `f5` is the key: the activity hash, or the bubble id (`0x8001_00xx`).
  - In The Devil's Lair, the solo client advertised its strike session with 2 open slots while it searched, so a strike playlist fills by others joining in progress.
  - Bubble searches ask for 3 slots. That is the fireteam's reservation, as GDC 2015 describes it.
- **The search level `f3.2`.**
  - Bubble searches always got 400.
  - Activity searches got 100 for the first 10 s, then 200, 300 and 400 in steps of about 5 s, measured by the search's own elapsed time (`f13`).
  - `RelaxationRule` reproduces this, and its test uses the captured pairs as targets.
- **Configurations (kind 4).** There are three. Every reply for one content hash was identical:
  - strikes (content `0xf502dd07` → config `0xf1b7ad41`);
  - social (`0x5ec025c8` = fnv1 "social" → `0xfab9fd14`);
  - everything else: story, raid, patrol (→ `0x9ce4d119`).

  The fixture encodes byte-identically to the live strike configuration (checked against the capture locally). Searches quote the configuration hash back in `f7.2`. These are stand-ins for 56578, whose client is known to read only the presence of `f4`.
- **No party messages.** BAP 36-41 (friends, party invites) never appear. On the 360 the fireteam was the platform's. On PS4 it is the PSN Session WebAPI (`ps4/design/peer-and-platform.md` §3.4, §4).

## What was built

- **Identity** (`d1_mp::identity`). This is the shared types module.
  - The types are `AccountSoid`, `CharacterSoid`, `PlayerKey {account, character}` (the player store's key), `FireteamId`, `ConnectionId`, `OnlineId`, and `MemberIdentity`. `MemberIdentity` is the 40-byte `{machine, player, account, character, fireteam}` of a join request and of each membership member.
  - Accounts follow the player store's scheme (#307):
    1. explicit bindings, with the responder's `--npid` keeping `D1_ACCOUNT_SOID`;
    2. then the store's `identities.json` through a `Resolver` when `D1_STORE=1`;
    3. otherwise the same allocation in memory: `0xD101_0000_nnnn_n001`.
  - One live connection per account.
  - BAP 23 now gives each platform id its own SOID. Before, everyone got `D1_ACCOUNT_SOID`, so a client would read its fireteam-mate as itself.
- **Fireteams** (`d1_mp::fireteam`).
  - Everyone is always in a fireteam, from sign-on. The client keeps its fireteam session from sign-on.
  - Supports invite, accept, decline, join a member, leave, kick, promote and join policy.
  - The cap is the selected activity's `maxParty`: 3 for most activities, 6 for raids, never above 6. With nothing selected it is 3.
  - Launch checks `minParty..=maxParty` and fails with the client's own `fireteam_size_requirment_failed`.
  - The leader passes to the earliest member who is still connected.
  - A disconnected member keeps their slot for the reconnect grace.
  - A join while the fireteam is in an activity returns that activity's host id (join in progress). A Crucible match in progress refuses fireteam joins.
- **Matchmaking** (`d1_mp::matchmaking`).
  - `Directory` answers 42 with the replies above. It offers the emptiest session that has room, then the oldest (stream O3: the one placement rule, as the public registry places; it was the fullest first). A search never offers the searcher's own fireteam's sessions, or a session too small for the searcher's whole fireteam. A public-bubble search the registry places is answered with the placed instance's advertisement (`handle_placed`).
  - `Matchmaker` runs playlists:
    - **Cooperative** (strikes): placed at once, in the emptiest open instance of the playlist that has room (stream O3; it was the fullest), else a new one, rotating through the playlist's activities.
    - **Versus** (Crucible): queued, oldest first, until `min_players` whole fireteams fit into the teams.
  - Teams are **not** assigned: the client's `team_picker` does that peer-side.
  - `place_in_public` fills public bubbles through the `PublicInstances` trait.
- **Platform sessions** (`d1_mp::platform_session`). This is the PSN Session WebAPI as a store, keyed by session id.
  - Each `POST /v1/sessions` keeps its own 78-byte `session-data`. The first id is the responder's old constant.
  - `GET .../sessionData` returns the record byte for byte.
  - Also served: members (`POST`, `DELETE`), `changeableSessionData`, `GET /v1/sessions/{id}`, and invitations (`POST .../invitations` with `invitation-request` `{"to": [...]}` and `invitation-data`). An invitee lists its invitations and fetches the data.
  - Presence `gameData` is kept per online id.
  - The multipart parts are found by `Content-Description`.
- **Shared activity instances** (`d1_activity_host::group`).
  - Connections whose join request names the same host (`+0x08`) share one instance.
  - Everyone gets one `replicate_membership`. Slot `i` holds member `i`'s own identity and properties, echoed. Both occupancy masks have a bit for each occupied slot. `+0x5020` acknowledges the elected physics host. The update number advances on every change.
  - Each member is granted 500 entity indices by its peer slot, as every live host did.
  - The first member is elected physics host. When the physics host leaves, the earliest remaining member is elected. A claim is granted only if nobody holds the role. The activity host may move it.
  - A closed connection leaves the instance when its `GroupLink` is dropped. Other members re-publish their membership on their next poll.

## Interfaces for the other streams

- **C (player store):** `d1_mp::identity::{AccountSoid, CharacterSoid, PlayerKey}` are plain `u64` wrappers of the store's keys. `Resolver` is how the multiplayer services ask `identities.json`; `mp::init` wires it. Stream O3 closed the open part: the responder serves several players' records at once, keyed by identity, and each player's own primary BAP connection gets its QueueZ deliveries (`d1-responder/src/players.rs`; the wiring note's O3 section).
- **G (public instances):** implement `d1_mp::matchmaking::PublicInstances`:
  - `instances(bubble) -> Vec<PublicInstance {host, players, reserved, capacity, started_ms}>`;
  - `reserve(host, slots) -> bool`.

  Then `place_in_public(bubble, reservation, &mut registry)` returns `Join {host}` or `StartNew`. A public instance's clients share membership through `group.rs` when they name its host.
- **J (Crucible, strikes, raids):**
  - `Matchmaker::add_playlist(Playlist {hash, kind, activities})`, using `PlaylistKind::Cooperative {max_players}` or `Versus {teams, team_size, min_players}`;
  - `Services::launch_playlist(leader, playlist, party, now)` and `Services::tick(now) -> Vec<MatchFormed {playlist, activity_hash, match_id, fireteams, players, joined_in_progress}>`;
  - `Services::launch_activity(leader, ActivityRef {activity_hash, party, host, joinable_in_progress})` for direct launches. `party` comes from the content's `minParty`/`maxParty`.
- **The activity host:** `ActivityInstance::set_group(GroupLink)`. The listener does this under `D1_AH_SHARED_INSTANCES=1`.

## Tests

- `d1-mp`: 29 unit tests and 7 scenario tests (`tests/scenarios.rs`), all passing. The fake clients sign on, translate ids, advertise and search with real 42 bodies, form and break fireteams, disconnect and reconnect, and launch raids, strike playlists and Crucible.
- `d1-bap`: 8 new tests in `matchmaking_sessions`. All 20 tests whose names contain `matchmaking` pass.
- `d1-activity-host`: 6 `group` tests, including two `ActivityInstance`s through the hook end to end. All pass.
  - In the crate's full run (118 passed), 10 codec and controls tests fail. They need the owned eboot (`D1_EBOOT`) and do not skip without it (`Eboot("The system cannot find the path specified")`); none of them touch the group code.
- `d1-responder`: one test that every hook declines with `D1_MP` unset.

## Open

- **Never seen in the game.**
  - Whether 56578 keeps 51539's field numbers inside `f7`/`f8` is `[I]`. The base fields decode alike in both builds.
  - What the PS4 client puts in an advertisement's session (likely its 78-byte record) is not known. The directory treats it as opaque.
- **The search scores** (`f3`, `f5`) and which candidate the live service chose are stand-ins.
- **BAP 23 sign-on.** The connection's own id is taken to be the first one it asks to translate `[I]`. The WebAPI identifies callers by bearer token, so whether the client names its online id on the session routes is `[U]`.
- **Peer slots.**
  - With shared instances, the PAH region record's per-peer token is still written at the configured peer index, not at each member's slot.
  - Later `allocate_entity_indices` requests are not confined to the slot's range.
- **Reconcile.** A physics-host migration is recorded and re-published, but the new host is not yet sent the sensor state as a reconcile.
- **shadNet rooms.** The Matching2 rooms in `shadnet-server` already hold several participants. D1 does not use them, so nothing here changes them.
