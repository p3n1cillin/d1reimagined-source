# PS4 56578 blockers, 15 Oct 2026

## The dark, dull world is an emulator texture-cache bug, half fixed (runs `dw-clock`, `dw-readback`, `dw-expand`, `dw-expand2`, 00:20–00:45)
- **User report:** "everything is so dark and dull". Measured: in world, 50–92% of the frame is pure black (luminance < 8) on every map (The Dark Within 51–75%, highway ~50%, Bannerfall 92%). Only directly sunlit surfaces render; ambient and bounce light are missing.
- **Ruled out:**
  - The GPU: shadPS4 uses the RTX 2060 SUPER (d1preservation's llvmpipe trap does not apply here).
  - The brightness setting: the first-run wizard set to 5 lifts the image only slightly.
  - Readbacks: `readbacks_mode = 1` + `readback_linear_images_enabled` changed nothing (config restored afterwards; backup `cfw-staging/2026-10-15-shadps4-config.before-readbacks.json`).
- **The world clock** (public `8d20ba3`, `D1_AH_TIME_BASE_MS`): 56578 `0x2A19D0` = blob `+0x520` (u64 ms) + elapsed sim time; `0x6E89E0(period)` = `fmod(clock / period, 1)`. Serving `now` moves the sun and shadows, so it drives time of day. It does not fix the black.
- **Cause found in the emulator log:** ~10,500 `Image overlap resolve failed` and ~150,000 `SanitizeCopyLayers: Coercing copy source layers N and destination layers N+1`. On that failure path `TextureCache::FindImage` **frees the cached image** and re-creates it from guest memory, discarding what the GPU had rendered into it.
- **Fix 1** (`tools/ps4_setup/shadps4-0.19.0-texture-cache-d1.patch`, built into `<D1_ROOT>\tools\shadPS4\0.19.0\shadPS4.exe`; the old exe is `shadPS4.exe.before-expand`): when the cached image has the same type, format and size but fewer layers or levels, expand it (`ExpandImage`, which copies the old layers) instead of dropping it. Result on The Dark Within with the clock served: black 75% → 52%, mean luminance 29 → 39; the shaded side of the array dish is now lit by sky light. Failures halved (≈5,400 left).
- **What is left, exactly** (detailed log in the same patch): every remaining failure is one shape: a cached **3D 32×32×32** image (format 37) requested as a **2D array of 2–3 layers** at the same address (4,767 + 86 in one session). A 32³ volume built slice by slice and then sampled as 3D looks like the colour-grading/tonemapping LUT. Dropping it on every slice write would give exactly a crushed, dull image.
- **Next:** in the texture cache, let a 2D-array request at a 3D image's address render into that 3D image (a 2D-array-compatible view of the 3D image, `VK_IMAGE_CREATE_2D_ARRAY_COMPATIBLE_BIT`) or copy the slices back into it, instead of freeing it. Then re-measure the black share and compare with retail footage the user has seen.

## The colour-volume attempt (run `agr12`, 16:15) - reverted
- All remaining overlap failures were one address, `0x377B10000`, about 50 times a second: a 3D `32×32×32` RGBA8 image and a 32×32 2D image with 2 (sometimes 3) layers evicting each other.
- Tried: keep the 3D image for the 2D request (2D-array view of its depth slices; 3D images are already created `e2DArrayCompatible`), plus collapse barrier layer ranges to layer 0 on 3D images (without that, `image.cpp:259` asserts). Result: zero overlap failures and no crash, the cinematic warmer and brighter (mean 119 → 138), but **gameplay almost black** (mean 147 → 3). Reverted (binary `shadPS4.exe.before-volume` restored; the attempt is kept in the session scratchpad).
- Reading: before, the volume was re-created from guest memory every frame, so it held whatever the CPU/content put there; keeping the GPU copy keeps whatever the 2-layer writes produce, which is wrong for gameplay. How the game fills that memory (CPU upload, compute, or slice renders, and what the 2-layer target really is) has to be measured before changing it again, e.g. a RenderDoc capture of one gameplay frame.

## Where each Earth mission starts, from content, and why only A Guardian Rises can start accurately today
- Scenario records (`<world>:scenario_client` `+0x48`: 22 × {bubble name hash, array of 0x3C slice-set records {+4 set name hash, +0x10 3 × u32 flags, +0x34 bubble hash, +0x38 set tag}}). The bubble hash is the region hash the client prints (`PRV08.08` = bubble 1 `0x69F9E3F6`, `PRV112.1` = bubble 14 `0xD6AD210E`).
- A Guardian Rises has two mission sets: **113** `cosmo_m0_phase00_highway_intro` and **105** `cosmo_m0_phase04_outro` (flags 1/1/1). Every other Earth story world has one set per bubble.
- The public bubbles (flags `6/2/6` or `9/3/6`) are the same in every story world: **0** Skywatch, **6** Mothyards (`delta_n`), **7** Steppes (`delta_s`), **11**, **12**, **20**.
- The missions open in those public bubbles: Restoration's phase00 is `delta_s` (7), The Warmind's is `delta_n` (6), The Last Array's is `array` (0), and The Dark Within's Ghost lines start on the way to Skywatch (0). In retail they began in shared patrol space.
- **Blocker:** a public region needs `sstm+0x141 == 2` ("connected"). Inside the slice-set manager (`0x740000–0x7A0000`) that byte is only compared, never written; it comes from the "PUBLIC activity" matchmaking path (`world_controller:matchmaking_manager: 'PUBLIC activity' …`), i.e. a second, public activity session. Serving that is the work that makes the other four missions start where they should. Until then, a private stand-in region (The Dark Within: 8) is the best available, and is labelled as such.

## Why "Enter the Wall" never activates: the objective handler's authority test (25 Oct)
- **Objective handler** = `0x40A8D0` (found by its `memcpy(component+0x1B0, state, 0x2F0)` at `0x40A964`). After the copy it computes "this objective is mine" at `component+0x4A4` from the player mask (`state+0x2C0`, copied to `+0x470`) against the 16 player slots - but only if the object's role byte passes `(role & 0xFB) == 1` (`0x40A9EC`; the same test is the helper ending at `0x40AD44`). The role byte is at `world + object pool offset + 0x78`.
- Live (run `agr-obj4`, watch at `0x40A9F2`): all 8 objectives are handled every 10 s; objective 3 holds our state 5 and mask `0xFFFFFFFF`, but its role byte is **0**, so the flag is never computed and the HUD/trigger logic never runs. The role byte's address moves between boots, so it cannot be pre-watched.
- **The sensor authority table** (public: `D1_AH_SENSOR_AUTHORITY=<machine>[,<seq>]`, `SensorAuthority::all_to`): `udt 5` `has_sensor_block = 1` carries a 65-bit changed mask and a 784-byte table (tag `0x80800CF7`, schema pointer `0x191A310` filled at load) decoded by the **replicated** decoder `0x2C9AE0` (presence bit first - the plain encoding decoded misaligned) into `world+0xA88`. Entries `{peer u8 @+1, seq u16 @+8, applied @+0xA}`; `0x2A1AB0` applies them via the game interface hooks (vtable `0x388` -> `0xBA2C20`, `0x390` -> `0xBA2CC0`, which maps a block onto a 0x600-byte entity mask). Served with all blocks to machine 14 (and, separately, 0x70), the table is stored exactly as sent and rung 34 completes, **but the objective role byte stays 0**. So authority blocks alone do not make the client authoritative for mission objects.
- `d1-agr-run.ps1`: the whole tutorial unattended (title, skip the Mars prologue - left playing it can trip the `BLOCK_DETECT` watchdog (`ud2`), skip both revival cutscenes, teleport), with an optional watch.
- Next: find what sets an object's role (1 = authority) - likely the physics-host election / simulation mode, not the AH's tables.

## Walking into The Breach: the client-driven bubble switch (runs `2026-10-26-agr-breach3`–`7`)
- Walking from the Wall into The Breach, the client starts `transitioning:normal_z_leg` to `PRV24.24` (hash `0x441515C2`, bubble 3) with token 3, and names the target in **udt 21** (`+0x158` index, `+0x15C` hash). The AH now moves the region record to that target with the next token (`follow_slice_target`). A target without its hash is a delta artefact (udt 21 is a replicated delta) and is ignored.
- It still waited for "valid host-tabulated data". Live (`sstm` read at `0x781623`): pending region 24, token 3, peer 0, and our record **was** in the client's membership copy, but `sstm+0x490` stayed −1. The copy routine (`0x778D60`) re-tabulates only when the membership **update number** (image `+0x00`, the client's `MEM-%d`; it logs "membership update '%d'") differs from the last one processed (`sstm+0x3B0`). We always sent 1, so the client never re-read the record. The teleport had worked only because a transition reset clears `+0x3B0`.
- Fix: the AH starts at 1 and advances the update number on every changed re-publish; the join and the udt-17 refresh re-send the same number, so their byte-identical control still holds. With it, `PRV24.24` "is being assigned the slice-set-switch task" and the Guardian walks on into the Breach (dark: the colour-LUT bug).
- **How the z-leg ends** (`0x77F480`, transition type 3): the player's current map cell lists (slice set, distance, kind) entries (`0x307F80` iterator, static content). The nearest other-set entry's distance is compared with three thresholds (42.5 / 85 / 127.5): the level is 3/2/1 below them and 0 beyond, and 0 (or no entries) stops the transition as "completed". In the dark room near the rifle the cell reads slice set 112 at 99.17, level 1: the return leg to 112, i.e. the client is in 24 with 112 as its return target. That matches the 01.24 natural crossing ("current 24 / target 112", engine phase 3, never idle 24), so the missing "completed" line is not a blocker.
- Mission steps can now wait for the client's current slice set: `%24|900` (udt 21 `+0xB8` index, `+0xBC` hash). That is the 01.24 mission's `{"on": {"type": 21, "slice_set": 24}}`, from which the Breach steps hang (Investigate, the Ghost-light trigger, dialogue, squads, the rifle). Slice sets 112 and 113 share the name hash `0xD6AD210E`, so the teleport's delta carries no hash and is not reported; 24's is.
- The Breach sensor list (captured live in bubble 3) has 249 clients: 141 new in group `0xFC0E45A3` (the Breach props, Ghost and Fallen squads), triggers `0x1D/34–36`, and dialogue sequences in `0x3C2F5ED5`. The 01.24 object ids (`missions/a_guardian_rises.json`) carry over unchanged.
- Run hazards: the client returns to Orbit for inactivity when the Guardian makes no progress for several minutes (a wedged walk, or exploring in the dark). `d1-walk.py --scan` now rescans around its first fix when it tracks fewer than 100 copies.
