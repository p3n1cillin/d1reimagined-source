# PS4 56578: cinematic binding registration (5 November 2026)

**Result: two reflected component registrars, not an ordinary C++ vtable.**
The sequence and video cinematic components register their owning entity through
`0x4E3910`. A matching registration is required before the cinematic sensor can
start playback. The component-construction path and its later callbacks are
recovered below, but the last interface-to-registrar dispatch selection and a
host-visible readiness acknowledgement remain **open**. This is not yet a
complete server readiness gate or a demonstrated fix for cine-live8.

This follows the addendum to
[the cinematic-start investigation](ps4-56578-cinematic-start-2026-11-05.md)
on `tools/ghidra-lines` ([PR #289](https://github.com/p3n1cillin/d1reimagined-source/pull/289))
and the GDC activity-host note on `note-gdc2015-architecture`
([PR #288](https://github.com/p3n1cillin/d1reimagined-source/pull/288)).
**Binary** means static inspection of the owned PS4 build 56578 executable,
SHA-256 `672f03411c0503dfbcda804cbb9fb27cdd9a8d73a8bcb71bf0c4f688073b0833`.
All executable addresses below are its vaddrs. **Repository** means checked-in
code, fixtures or earlier reports; **inference** and **open** are explicit.

## The two registrars and their dispatch records

**Binary.** ELF relative relocations give these function-pointer slots:

| Method | Pointer slot | Containing reflected method list | Role established by its body |
| --- | --- | --- | --- |
| `0x4E7470` | `0x1999E88` | `0x1999E70`, 38 records | Initialise sequence component state |
| `0x4E7590` | `0x1999EA0` | same | Clean up sequence state and unregister `component+0x2C` |
| `0x4E7C70` | `0x1999EB8` | same | Prepare child bindings, then register `component+0x2C` |
| `0x4F1650` | `0x199A2E0` | `0x199A2E0`, 33 records | Acquire/use the video-system service |
| `0x4F16F0` | `0x199A2F8` | same | Unregister `component+0x2C`, then release the service |
| `0x4F1790` | `0x199A310` | same | Load `component+0x2C` and tail-call `0x4E3910` |

These are **24-byte reflected member-function records**, containing a function
pointer, a `this` adjustment and signature/flags. They are not eight-byte C++
vtable slots. An audit through the existing `d1_eboot::rtti::harvest` found none
of the three requested methods in its C++ vtables. The repeated signature hashes
do not recover method names.

**Binary.** Initializer `0xBF5670` associates the first list with the runtime
reflection type cell `0x28E6A20` (through pointer slot `0x19B1C08`), and the second
with `0x28E6C80` (through `0x19B1C20`). It registers the containing collection
through `0x1D2830`. The shape pointers assigned by `0xBFD960` are `0x1937CE8`
and `0x1937E38`; their size words describe runtime sizes `0xF0` and `0x40`.
These cells identify the two classes without inventing a C++ symbol spelling.

**Binary / descriptive class names.** The first is the **sequence cinematic
component**: it maintains a current segment at `+0x38`, segment arrays, child
bindings and preload state. Its identifier getter `0x4E6E20` is at
`0x1999F00`, and its start implementation `0x4E9B20` at `0x1999F18`.
The second is the **video cinematic component**: it uses `c_video_system`, whose
actual RTTI is `0x1914B90`, vptr `0x1914B60`. Its shared identifier getter is at
`0x199A358`, and its start implementation `0x4F18B0` at `0x199A370` calls the
video request routine `0x33E0D0`. The two component names here describe their
behaviour; their original authored class names were not recovered.

**Binary.** There are two direct transfers to the appender: the call at
`0x4E7EB0`, inside `0x4E7C70`, and the jump at `0x4F1793`, inside the separate
three-instruction callback beginning at **`0x4F1790`**. Ghidra's function
containment at the latter boundary is misleading: its decompile can associate
the jump with the preceding cleanup function. Read the instructions and
relocation slot, rather than treating `0x4F1793` as a third registrar function.

## Construction, placement and the remaining dispatch gap

**Binary.** The ordinary entity constructor `0x32DBF0` allocates from the pool
headed by `0x2692220`, then calls `0x30AE30` to allocate/construct its component
tree. Component initialisation runs through `0x30D930` and `0x1D0D30`; after a
successful initialiser, `0x30D930` stores the owning entity handle at the runtime
component's **`+0x2C`**. Thus this field is neither a sensor index nor a cinematic
resource hash.

The constructor then calls `0x32DF20`. That path calls `0x30ECD0` with the entity
and its component-allocation handle. `0x30ECD0` enumerates implementations of
the interface selected through `0x191AB10`, resolves each member binding and
dispatches through `0x353610` at `0x30EE05`. It subsequently calls
`0x30EEC0`, which computes component state masks and dispatches another family
of notifications through `0x30F9D0`. These are real post-construction/component
state paths, separate from cinematic sensor apply `0x403140`.

**Inference, strong but not a completed indirect-call proof.** The adjacent
initialise / cleanup / register methods, the freshly assigned owning handle,
and these post-construction notifications make entity placement/content
instantiation the leading explanation for running `0x4E7C70` or `0x4F1790`.
This is more specific than "when the sensor value arrives".

**Open.** `0x353610` is an erased dispatcher used by many unrelated interfaces.
It reads the selected interface's method binding at table offset `+0x30`;
finding a call to it does not prove which concrete callback it selects.
The instantiated content's interface mapping still needs to connect that
notification to slot `0x1999EB8` or `0x199A310`. Consequently this investigation
does **not** establish whether the relevant cinematic object is placed directly
by bubble residency, by an earlier object's auth-state reconciliation, or by
another component activation. Nor does it establish which of the two concrete
classes cine_reveal or cine_speaker instantiates.

This boundary matters for the GDC model. The talk's reconcile reuses placement
code; therefore "placement callback" and "caused upstream by auth state" need
not be alternatives. The talk alone cannot identify this client's missing
message or readiness report. No additional host message is justified by the
method table alone.

## What is registered and what `+0x68` means

**Binary.** `0x2692220` is the **general owning entity/sobject pool header**:
its data pointer is at `+8` (`0x2692228`) and stride at `+0x10`
(`0x2692230`). `0x32DBF0` allocates its records and copies the entity type from
the authored definition's `+0x8E` into record `+8`. This is not a dedicated
cinematic-handle table. It is also the entity pool documented by
[the native squad reader](ps4-native-squad-targets.md#what-the-reader-follows).

`0x4E3910` masks the supplied owning handle with `0x1FFF`, uses that pool's
reported stride, and asks `0x337FE0` for the cinematic interface selected through
`0x191ACE0`. `0x337FE0` delegates to the normal component/interface walker
`0x30E5E0` / `0x30E240`, using entity `+0x54` to reach its component tree.
It does not turn the entity-table index directly into a cinematic id.
`0x354400` dispatches the resolved interface's identifier getter; the two
implementations above use `0x4E6E20`, which reads **definition `+0x60`**.

**Binary.** `0x403770` resolves the cinematic **sensor component's authored
definition** through its definition handle and offset (runtime component `+0`
and `+8`). It reads a 32-bit name/id at **that definition's `+0x68`** and passes
its address to `0x4E3F70`. This is the key compared with the registered
interface's identifier. It is not runtime `component+0x68`, a pointer to a
binding, the replicated counter, or the sensor group's wire hash.
The sensor definition's `+0x68` and the playback component definition's `+0x60`
must name the same cinematic. Their actual per-world values must come from
loaded content, not a guessed constant shared by activities 165 and 167.

**Binary correction to the addendum.** Let `G = *0x26AFEF0`. The count is
`G+0x1350`, the capacity check is 32, and the **first entry is `G+0x1358`**,
stride `0x38`. `G+0x1320` is the one-entry-before cursor used by some loops.
The appender writes the first entry's pending byte at `+0x1358`, owning handle
at `+0x135C`, and resolved binding beginning at `+0x1360`.
At capacity it returns without appending; interface lookup failure also leaves
no entry. Registration is therefore necessary but not guaranteed by merely
constructing some entity.

## Incident values: BSS, initialisation and catalogue matches

**Binary.** The ELF headers give the writable `PT_LOAD`:

| `p_offset` | `p_vaddr` | `p_filesz` | `p_memsz` |
| --- | --- | --- | --- |
| `0x18DC000` | `0x18D8000` | `0x149530` | `0x16927D0` |

File-backed bytes end at vaddr **`0x1A21530`**. Both `0x2651C90` and
`0x2651C94` lie past that boundary, inside BSS. They have **no valid file
offset containing their runtime u32 values**. Applying a blanket `+0x4000`
would be an invalid read, not an incident lookup.

The values are assigned by initializer `0x24DA20`:

| Global | Runtime value after initialisation | Store instruction | Store's file offset |
| --- | --- | --- | --- |
| `0x2651C90` | `0x3C03F059` | `0x24DB67` | `0x251B67` |
| `0x2651C94` | `0xAECA3822` | `0x24DB74` | `0x251B74` |

The instruction offsets above use the executable `PT_LOAD` (`p_offset=0x4000`,
`p_vaddr=0`), independently of the writable-segment calculation. The existing
offline cinematic-start tests also execute this initializer and check these
two assigned values; that test result is from the earlier investigation,
not a new execution in this task.

**Repository catalogue check.** The retained 01.24 catalogue report
`JOIN218-incident-catalog-report.json` gives hash `0x3C03F059` at index **734**
and `0xAECA3822` at **2120**, both payload selector 17. The latter match was
already described in [incident diagnostics](incident-diagnostics.md).
[The capture note](d1-live-captures-2026-11-05.md#what-decodes) correlates
734/2120 on 51539 with **891/2681** on PS4 56578. This is a catalogue plus prior
capture correlation; a complete 56578 catalogue was not newly extracted.

**Consequence.** The unsuccessful start in `0x403770` uses the same hash called
"cinematic stopped" in the captures. **891 is not a unique start-failure
acknowledgement.** A successful start uses the started hash, correlated with
2681. The reporter also requires a local player; absence of an incident does
not isolate the failing gate.

## Host ordering and the checked-in fixtures

**Required client conditions, from the binary; proposed host ordering:**

1. Load the selected activity, destination and slice set, and complete the
   normal content/entity instantiation and applicable reconcile. Establish a
   valid local player. Discover the PS4 sensor records for that loaded world.
2. Establish that the playback component whose definition id matches the
   cinematic sensor definition `+0x68` has registered in `G+0x1358`. The
   appender's completion and the matching entry are the concrete internal gate.
   A successful class-specific start is an additional condition.
3. Apply the idle baseline and then send `playing=1` with a new counter derived
   from that record's last served value. Keep the proper absent object reference
   and filter `-1` unless deliberately selecting a player. A rejected attempt
   consumes its counter; repeating it after readiness changes does not retry.
4. Use a started report naming the intended cinematic record as evidence of
   acceptance. Follow its completion before advancing the next authored beat.
   Any deliberate retry needs another counter change and a reason to believe
   the failed prerequisite changed.

**Open host gate.** No decoded upstream wire field in this investigation proves
step 2. `in_world`, slice-set membership, sensor enumeration and `pending=0`
are insufficient evidence on their own. The checked-in native reveal list has
kind-6 A schema `0x8080254D` and **no B schema** (`0xFFFFFFFF`); it does not
provide a demonstrated cinematic-ready sense value. This does not rule out a
readiness report elsewhere. Do not replace that missing correlation with a
fixed delay, a new guessed host message, or a blind play/retry loop.

It does not gate the setter, but should be corrected or replaced by an empty
list when preparing a controlled host change. No fixture was changed here.
