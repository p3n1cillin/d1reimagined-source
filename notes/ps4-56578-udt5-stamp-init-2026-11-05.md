# PS4 56578: udt 5 stamp and init (5 November 2026)

**Result: the stamp anchors a client clock; init latches permission to consume
entries.** The applier does not reject a lower stamp. Repeating init=1 does not
reset replicas or the cinematic's change counter. Per-entry `fresh` and the
values sent in the entries are separate from frame `init`.

This is **offline static analysis** of the owned PS4 **build 56578** executable,
SHA-256 `672f03411c0503dfbcda804cbb9fb27cdd9a8d73a8bcb71bf0c4f688073b0833`.
All executable addresses below are this build's vaddrs. No emulator, route,
input, watchpoint or native capture operation was performed. No new in-game
behavior or emulator commit is claimed. AI-assisted: yes, OpenAI Codex.

The framing observed previously is in the
[live timeline](d1-live-speaker-timeline-2026-11-05.md); cinematic counter behavior
is in the [cinematic-start investigation](ps4-56578-cinematic-start-2026-11-05.md).
No capture was decoded or copied for this investigation.

## Answers to the four questions

| Question | Status | Answer |
| --- | --- | --- |
| 1. Does stamp reject or reorder frames? | **Established for the traced receive/apply path** | No stamp comparison or sorting. A ready world with matching gen stores the new stamp, even zero after a higher value, before consuming init/entries. Clock estimates can remain clamped at their previous values after such a backward anchor. Transport-level ordering is outside this finding. |
| 2. What does init do? | **Established** | One sets a persistent walker latch; zero requires that latch already to be set. It does not clear pending entries, default every replica, or reset the cinematic record. Repeated full frames can still overwrite state through their entries. |
| 3. Is an empty heartbeat only a stamp write? | **Established, conditional on walker readiness** | It also records receipt clocks. After the init latch is set it reaches the ordinary pending-completion check and, if that succeeds, reconciliation/dispatch bookkeeping. It does not itself mark an entry dirty or satisfy a pending entry. |
| 4. Timeout, lag or ordering use? | **Established clock use; timeout remains open beyond this path** | Stored stamp plus time since receipt drives two extrapolated, nondecreasing clock estimates. No stamp-age drop or stamp-based disconnect threshold was found in the traced functions. This is not an exhaustive absence proof for all client watchdogs. |

## Re-derived addresses and receive path

**Established.** The address labels in the current `d1-oracle/src/sensor.rs`
module introduction must not be used as 56578 function identities. In this
image `0x2A1210` is a loop comparison inside world setup at `0x2A0D20`, and
`0x29D3F0` is not the raw udt-5 receive handler. The actual paths were recovered
from the loaded-image layout, calls and relocation addends, rather than by
applying a common address delta:

| Stage | 56578 evidence |
| --- | --- |
| Message-id dispatch | The 16-byte row at `0x19104E0` has id **5**; its relocated callback at `0x19104E8` is `0x29DDF0`. The dispatcher `0x299E30` searches these rows and calls the selected callback at `0x299E98`. |
| Raw receive | `0x29DDF0` passes payload and length through `0x2408E0` at `0x29DE27`. Its client-state flag can suppress forwarding; it does not parse the stamp. |
| Game interface | `0x2408E0` calls interface slot `+0x338`; installed table `0x19439A0` has `0x6E8DA0` at `0x1943CD8`. This wrapper calls `0xBB1C10`. |
| Queue construction | `0xBB1C10` allocates type **0x13** at `0xBB1C56`, stores payload length at element-data `+0x58`, copies the raw bytes to `+0x5C`, then enqueues. It does not decode the header. |
| Queue consumption | Type 0x13's switch target is `0xBB4797` in `0xBB4690`; it calls `0xBB1D00`, which resolves the world and tail-calls **`0x2A1C40`**. |
| Frame decoder | `0x2A1C40` reads gen, optional authority block, stamp, and calls walker **`0x2D0CD0`** for init/entries. |

The optional authority block is handled **before** the gen/readiness gate. Its
effects, including the conditional local deadline write at `0x2A1DD5..0x2A1DDB`,
must not be attributed to the stamp. The minimal heartbeat has no such block.

## Stamp: unconditional anchor replacement after the gen gate

**Established.** In `0x2A1C40`:

- `0x2A1E71..0x2A1E76` reads the 32-bit stamp.
- `0x2A1E7B..0x2A1E8C` requires `world+0x1C != 0` and decoded gen equal to
  `world+0x1D`. This compares the **gen byte**, not the stamp.
- `0x2A1E8E..0x2A1E94` passes the stamp to `0x2A2910`, using the object at
  `world+0x10` as its receiver. Call that object **clock state** below.
- `0x2A1E99..0x2A1EA7` then calls the walker at `world+0x28`. Thus even an
  init=0 frame received before the walker latch is set updates the clock anchor
  if the world/gen gate passed. Anchor replacement also precedes entry decode
  success; it is not conditional on successful reconciliation.

**Established.** `0x2A2910` does these stores without consulting the old stamp:

| Clock-state field | Store |
| --- | --- |
| `+0x3C` | New frame stamp, at `0x2A2919`. |
| `+0x48` | Current local clock, at `0x2A2933`, using the cached clock at `0x26553A8` or `0x694D0`. |
| `+0x50` | Current game-clock counter from `0x241180` when `0x2411B0` permits it, otherwise -1, at `0x2A294C`. |

There is no last-stamp, world-tick or gen comparison in this routine. The raw
receive and queue-copy stages likewise do not decode a stamp to order by it.
**Inference:** a valid frame stamped zero after a higher stamp is processed by
this path, but repeatedly re-anchoring to zero can prevent useful clock progress.
That is different from silently dropping its entries.

## Init, fresh, pending and cinematic state

**Established.** Walker `0x2D0CD0` consumes init first:

- `0x2D0CFB` reads the bit. One stores **1** at `walker+0x62C` (`0x2D0D04`) and
  continues to the entry loop. It does not loop over replicas at this point.
- Zero tests that byte (`0x2D0D1E`); if it is still zero, the walker returns
  without reading entries (`0x2D0D2F` to `0x2D15BC`). Otherwise it continues.
- Explicit lifecycle reset `0x2D04D0` clears the byte. World re-setup `0x2A1310`
  calls that reset at `0x2A139D`. Frame init=0 does not clear it.

**Established.** `fresh` is a different, per-value bit. For an eligible named
entry, the A path reads it at `0x2D0E90`:

- Fresh=1 calls schema default initialization `0x2CA4A0` on the replica buffer
  (`0x2D0EB6..0x2D0EBC`) before applying the decoded overlay.
- Fresh=0 uses the actual replica buffer when **entry pending byte `+0x15` is
  zero**. When that byte is nonzero it redirects decode to scratch and does not
  treat A as successfully initialized (`0x2D0EF1..0x2D0F02`).
- The B path has the same pending/fresh distinction (`0x2D0F81..0x2D0FD0`).
- A successfully accepted entry sets its dirty byte `+0x66`, stores its B flag
  `+0x16`, and clears its own pending byte `+0x15` while decrementing the pending
  count (`0x2D1050..0x2D1079`). These stores are not performed for omitted entries.

Consequently the module introduction's unqualified statement that fresh=0 is a
discarded-scratch no-op is too broad: that is the **pending-entry** case. Deltas
can overlay an initialized replica. Frame init=1 does not change how that choice
is made and cannot make a pending fresh=0 entry initialize successfully.

**Established / inference applied to the host.** Repeated init=1 alone cannot
reset a playing cinematic or zero its counter. Fresh initialization targets the
replica value buffer; it does not first default the cinematic game record that
`0x403140` uses for its old-counter comparison. That setter copies the received
value into the game record, then reacts only to a counter change, as established
in the linked cinematic note.

A repeated full frame's **contents** still matter. Resending an older stopped
value with a different counter can stop a playing record; a different playing
value can request a transition. Repeating an unchanged counter does not create a
new start attempt. Omitted entries are not defaulted by init. The whole-frame
flag is therefore not an explanation for resetting all cinematic state every
ten seconds, nor does changing only init fix a consumed cinematic counter.

## Empty frames and the completion pass

**Established.** The minimal frame is 43 meaningful bits: gen (8), no authority
block (1), stamp (32), init (1), has_entry=0 (1), padded to **6 bytes**. The stamp
stores above occur even when it has no entries.

If init=0 and the latch is unset, the walker exits at its initial gate. With the
latch set (or init=1), has_entry=0 goes from `0x2D10A3..0x2D10AA` directly to
`0x2D1600`, the pending-completion check, at `0x2D10BA`.

That check rejects completion while an entry with pending `+0x15` belongs to the
local machine or has an unassigned owner (`0x2D1732..0x2D1757`). A heartbeat
does not clear those pending bytes. On success the walker performs its normal
collection/dispatch sweep (`0x2D10C7..0x2D15BA`). In that sweep `0x2D2F20` calls
`0x2D2F30` with force=false; `0x2D2FDA..0x2D2FE3` gates A-value dispatch on
entry dirty byte `+0x66`, then clears it at `0x2D3013`.

Thus an idle, clean heartbeat does not reapply every value, default replicas or
restart cinematics. It still runs bookkeeping and may process already-dirty
state when completion is possible. Calling it strictly a stamp-only operation
would hide that shared completion path.

## Clock consumers and the timeout limit

**Established.** Stamp receipt is used for extrapolation, not merely logging:

| Routine | Dataflow |
| --- | --- |
| `0x2A2D90` | Reads stamp `+0x3C`, local receipt time `+0x48`, and configured period `+0x18`; derives elapsed whole periods since receipt and adds them to the stamp. Stores a nondecreasing seconds estimate at `+0x44`, then returns an integer tick estimate. |
| `0x2A2EF0` | Reads stamp `+0x3C`, saved game-clock counter `+0x50`, current counter `0x241180` and conversion rate `0x23FD20`; extrapolates using the same configured period. Stores/returns a nondecreasing seconds estimate at `+0x40`. |

The local-clock subtraction is at `0x2A2DF7`, the stamp addition at `0x2A2E22`,
and the first clamp/store at `0x2A2E51..0x2A2E68`. The game-counter subtraction
and stamp addition are at `0x2A2F55` and `0x2A2F7F`; its clamp/store is at
`0x2A2FA2..0x2A2FB9`. Missing receipt-clock sentinels select a stamp-only
calculation. The conversion constants read at `0x1622FB0` and `0x1622FDC` are
1000.0; paired +1/-1 float constants were also checked. No 10 Hz period was
hardcoded or inferred from a single captured stamp for this finding.

Direct callers include `0x7AF7E7` for the tick estimate and `0x3F9D40` for the
game-clock estimate; these values have consumers outside the decoder.
**Inference:** a progressing stamp and empty heartbeats keep the time origin
aligned. Repeated zero anchors can stall an already advanced estimate until
extrapolation catches up, especially if each resend replaces the receipt time
again. That supports the proposed live framing experiment without establishing
that it fixes any particular native failure.

**Open:** a complete audit of every lag display, connection watchdog and indirect
consumer. No stamp-based expiry/drop was found in the handler, queue builder,
applier, stamp setter or these clock estimators. The estimators keep advancing
between receipts; they do not themselves expire the anchor. The separately
observed authority deadline is not evidence of a stamp watchdog. The private
field-xref search is incomplete, so its missing readers are not an absence proof.

## Verification and handoff

The prebuilt `d1-eboot` was used without a cargo build. Its aggregate controls
confirmed the executable identity but **failed the reference-build fixed-address
controls**, as in the cinematic investigation. No aggregate PASS is claimed.
Before citing xref results, all four independently checked 56578 controls passed:

```text
--control call:0x12AA7C0:0x403177
--control jmp:0x3000B0:0x4F162C
--control riprel:0x1A1F100:0x403154
--control rela:0x402EF0:0x19A3850
```

`disasm --snap` was used to read enclosing prologue-anchored ranges, including
the misleading supplied addresses. Ranges that stopped at data were narrowed;
an early stop was not treated as a complete scan. `xref` independently recovered
the walker and applier callers. `rtti --name activity_client --slots` corroborated
the client dispatcher. `field-xref --global 0x2655750 --offset 0x3c` and `0x48`
were used with `--no-control` only for candidates: their reference-build controls
are unsuitable and their pool/indirection coverage misses known clock readers.
Their absence results are not cited as evidence.

The existing **file-only `d1guest.Image` reader** was used for the message-id row,
switch displacement and float constants, with executable SHA and independent
instruction-byte controls checked first. No live-reader instance was created.
Ghidra was attempted with no analysis, read-only project access, Idle priority,
one CPU and a bounded heap; it could not acquire the project lock. Its launcher
also initially could not write its settings. Logs/settings were directed outside
the repository; no decompilation result is claimed, and no project import or
copy was attempted.

This change contains the research note and its index only. No runtime behavior,
codec, fixture or test was added. Workspace tests and cargo builds were not run,
per the request to avoid load during a possible route run. Validation is the
bounded static cross-checks above, `git diff --check`, and the repository
conventions check with title `notes: establish 56578 udt5 stamp and init behavior`.

**Host handoff (inferred design guidance):** retain an initial complete delivery
with fresh values for pending entries, then use deltas for initialized entries
and derive progressing stamps from the host's clock. Init is not a periodic
reset command. Keep each cinematic's counter independent from the frame stamp;
advance it for a deliberate new command/retry. Empty heartbeats maintain clock
anchors but cannot replace missing initialization entries. Native confirmation
of the opt-in host mode and the runtime clock period remains future work.
