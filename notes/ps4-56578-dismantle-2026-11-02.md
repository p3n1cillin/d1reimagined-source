# PS4 56578: dismantling (2 November 2026)

Run sense118 on the owned 56578 image, served from `lab/hangar-retreat` with the responder from
`main`. Owned inputs and run output stay outside the repository.

## The request

In Tower North after an unattended A Guardian Rises, the Guardian was given a spare Khvostov:
- the post-game profile plus an unequipped Khvostov at slot 94 (`d1-character-fixup.py profile ...
  --item 94:3598:0xd10000000000030b`);
- pushed with its inventory element (`lab/tower-route/push_profile.py ... --item ... --soid
  d10000000000030b`).

The character screen showed both rifles under Primary Weapons, and the spare's tooltip offered
"✕ Equip  ◻ Dismantle", as in the original. Holding ◻ for 3.5 s sent:

```
INVESTMENT message id 402 (17 body bytes)
⭐ ITEM MOVE (402) (15B request): e880000000000185c7074000000000 -> accepted
```

The client's codec (`d1-oracle object --tag 0x80801767 --decode ...`) gives {`+0x00` 1 (instanced),
`+0x08` 0xd10000000000030b (the instance), `+0x10` 0x0E0E = 3598 (the content index)} and a zero
i32 above it (the quantity, 0 for an instanced item).

So 402 is `inventory_perform_item_action`, as Blam Network's 2014 live dictionary names it, and a
dismantle is one. The investment table had guessed a transfer, but that is 405. The responder
answered with the result composite and applied nothing, so the rifle stayed on screen: the client
waits for the server's profile change.

## Serving it

PR #210 makes the responder empty the item's slot and push the profile and account:
- it refuses an equipped item;
- yields come only from a `D1_DISMANTLE_YIELDS` table, one sourced row per item.

The yields were the original servers' rules, and the client data has none: the manifest's
`values` are bounty and engram rewards. Period reports say white gear gave Glimmer only (no
weapon parts), and legendaries gave Legendary Marks (and Silver Dust from Rise of Iron, patch
2.4.1.1). No amounts were found yet, so no row is filled in.

## What the client data says about a dismantle

The client data does describe dismantles, item by item. Every item definition (class `0x80801806`)
points at an action block (class `0x80801916`, Blam Network's `s_item_action_block`). Its type
hash `0xB2084C93` is FNV-1 of "shard", the dismantle. Next to it is a u16 that the client hands to
its reward resolver, with a reward item (-1 on every shard row).

`tools/ps4_setup/d1-item-actions.py` lists the block for all 7,544 items:
- 3,866 have "shard";
- 182 have "decrypt" (engrams) and 43 "open".

The u16 follows tier and bucket:

| Items | Value |
|---|---|
| Legendary armour (tier 4, buckets 7-11) | 730 |
| Legendary weapons (tier 4, buckets 2-4) | 739 |
| Rare armour | 729 |
| Rare weapons | 738 |
| Exotic weapons | 737 |
| Exotic armour | 728 |
| Tier-1 armour | 21 |
| Tier-1 weapons | 22 |
| The Khvostov (content 3598, definition `0x80A64722`) | 1117 |

So yields can be keyed by this value, about ten rows instead of one per item. The amounts themselves
are not in these blocks:
- the block's progression-reward list is empty on every shard row;
- the only global table with that many rows (investment global slot 0, 1,122 rows of 20 bytes)
  is records: row 22 hashes to `achievement_pvp_heavy_weapon_kills`.

The resolver (Blam: `sub_831B6368` -> `sub_831DE790`, investment vtable +488 on the 360) is the
next thing to read in the 56578 eboot. Until it is read, no amount is filled in.

### The silhouette and the zero stats (findings, not yet fixed)

- **The silhouette:** the character screen's Guardian (and the post-game Advancement screen's) is
  a solid black silhouette. The 01.29 research found that the preview widget
  (`cui::c_cinematic_texture_camera_widget`) builds its model from the appearance block of the
  family-3/1 card (`+0x68`) or the family-1/1 view (`+0xB60`) (`ps4/design/geared-guardian-fixtures.md`
  82-90). The world Guardian uses family 0/1 `+0x30`, which we serve in full.
  - 56578 runs never serve `D1_CHARACTER_FILE`, so family 3/1 is the responder's identity-only
    fallback, and family 1/1 has never been built.
  - The oracle notes that in 56578 only `0xA110F0` reads family 3, for the character-select tiles.
  - Test: serve a geared family-3/1 card (`d1-oracle character build --inventory .../inventory-tutorial`).
    If the silhouette stays, build family 1/1 next.
- **Intellect, Discipline and Strength read 0:** the general stat table the peer card serves
  (`+0x838`) carries only Light (`docs/PS4_CHARACTER_STATS.md`). Filling keys 2-7 1:1 needs each
  armour instance's own stat values. The manifest gives only ranges (e.g. Twilight Garrison Intellect
  51-86). Reading +0x24 of the served item elements as the content index mapped the "Helmet" file to
  a sparrow (S-35 Jealousy), so either that field or the file names need checking first.

## A host-crash repair mid-mission (sense125, 14:57)

At the second chest the client logged "it has been 4349 milliseconds since the last network
update", then "Lost connection to activity host (possible crash) (last received 23263 ms >
timeout (20000 + 500) ms)". It started its private-activity repair, which rejoined the activity
host and relaunched 164 from the start: the host published region 113 and served mission step 0.

The host had been answering; its log shows client frames at 14:57:04 and 14:57:10, and the
client's udt-15 notices stop at 14:56:49. That points to an emulator stall on the client side, not
the host. The replay exited ("unit unavailable"). It was restarted from the beginning against
a copy of the host log taken from the reconnect (`activity-host-attempt2.log`). Without that copy
`contains(RIFLE_EVENT)` would have matched attempt 1's rifle.

To do: the replay could detect a repair rejoin (a second "AH connection from" after gameplay)
and restart itself the same way.
