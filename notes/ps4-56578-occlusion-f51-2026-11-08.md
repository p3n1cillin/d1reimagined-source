# PS4 56578: lens flares and glare stop at walls (F51), 8 November 2026

The user reported lights and the tripmines' glare showing through walls. Destiny tests every lens
flare with a GPU occlusion query; upstream shadPS4 answers every query "fully visible". The fix is
fork PR [p3n1cillin/d1reimagined-shadps4#13](https://github.com/p3n1cillin/d1reimagined-shadps4/pull/13),
switched on by `D1_OCCLUSION=1` (the full-game profile sets it; the baseline profile clears it).

## How the game uses the query (build 56578)

- **Issue** (`FUN_00f80ae0`): a 48-vertex disc (a 16-gon) is drawn at the light, with no colour or
  depth writes, between two `PIXEL_PIPE_STAT_DUMP` events (ZPASS_DONE). The begin dump goes to the
  query's address and the end dump to address + 8. That is 8 render backends × {begin, end},
  128 bytes, which the GPU zeroes first.
- **Read** (`FUN_007e13e0`): the result is ready when bit 63 is set in all 16 qwords. The count is
  Σ (end − begin) over the backends. `FUN_01057390` stores it each frame; a result that is never
  read leaves the stored count at 0 (hidden).
- **Visibility** (`FUN_007fbd90`): `vis = clamp((count / area − 0.35) / 0.65, 0, 1)`.
  - `area = onscreen × (rx·W·0.5) × (ry·H·0.5) × π` is the disc's expected pixel area. The
    constants (−0.35, 0.65, 0.5, π) were read from the eboot.
  - Counts live at 0x26E4F08 and areas at 0x26E5108, uint[128] each.
- The flare draws are also wrapped in `SET_PREDICATION`, which the emulator does not implement. The
  draws always run; the intensity comes from `vis`.

## What the emulator does with D1_OCCLUSION=1

- After the first dump, every draw runs inside a Vulkan occlusion query, begun **precise**: the
  hardware's PERFECT_ZPASS_COUNTS are exact.
- Each dump finishes the draws before it, then writes the running sample total at once. Backend 0
  gets the total; the other backends get a zero difference. Every slot carries the valid bit.

## Runs (A Guardian Rises, scripted drive, 8 November)

| run | build | result |
|---|---|---|
| gh10 | queries, dump written later | no flare anywhere: the game read "not ready", so 0 |
| gh11, gh12 | synchronous dumps (+ precise) | no flare in the windows compared (they held no lamp in view; see gh19) |
| gh13, gh14 | + logging of short intervals | one disc per frame. State: 48-vertex list, depth GreaterEqual (reverse Z), no writes, 1920×1080 single-sample depth |
| gh15 | + the disc drawn again with the depth test off | in view: every sample passes. Partly covered: 14–82%. Hidden: 0 |
| gh16 | counts ×4 | no change in the windows compared |
| gh17 | upstream's stand-in values on the synchronous path | every flare is back, including the Breach's blue light: timing is fine, the values decide |
| gh18 | counts ×1000 | the stair-side starburst is back: it is mostly covered (under 35%) |
| gh19 | the fix, game memory sampled | stored counts and areas agree (279/289, 219/210, 2855/3423 …); lamps in view draw their starbursts and streaks |

The earlier "no flare anywhere" readings (gh11, gh12) came from comparison windows with no lamp in
plain view. Later in gh19 the Wall's corridor and gantry lamps flare normally (frames 047, 053,
059, 060, 068). The lights stable builds showed behind geometry (the stair lamp, the blue light past
the Breach fence) are now hidden, as the game's own test says they should be.

## Open

- **Tripmine glare:** it uses the same query path (other API users `0x7d1840`, `0x1055e80`,
  `0x1055fd0`). It has not been looked at on its own.
- **Cost:** the synchronous dump waits for the GPU twice a frame. It held the 30 FPS cap in every
  run; it has not been measured at 60.
- **Deployment:** the lab deploys the fork's `d1-occlusion-sync` 4429b3e (the #6 tree + the
  screenshot thread + these three commits). Fork #13 carries the same three commits onto `d1`.
