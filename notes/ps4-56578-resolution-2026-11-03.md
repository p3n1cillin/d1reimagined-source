# PS4 56578: render resolution (3 November 2026)

The goal (2 November): any resolution up to 4K, in the end chosen in the game's own settings menu.
Build 56578 renders 1080p on PS4. This note is the investigation so far; nothing here is in the default
lab patches.

## What the emulator offers

- **`GPU.internal_screen_width/height`** (config.json) is only the output resolution the emulator
  reports to the game (`sceVideoOutGetResolutionStatus`, `VideoOutDriver`). At 3840 x 2160 (session
  res-4k-a) the game still registered 1920 x 1080 display buffers and rendered 1080p.
- **`General.neo_mode`** (report PS4 Pro): with it and 3840 x 2160 (session res-neo-a) the buffers
  were still 1920 x 1080. The build has no Pro or 4K mode.
- FSR (`GPU.fsr_enabled`) only scales the finished 1080p frame for the window. No render-target
  scaling exists in this shadPS4 (0.19).

So more pixels have to come from the game: its renderer sizes everything for 1080p.

## The game's resolution

Three places, found statically (`lab/tower-route/static56578.py`, own dump):

- **0x7ED1C0** reads two 16-bit globals, **0x18DCC58 / 0x18DCC5C (1920 / 1080)**, clamps them to
  320..1920 x 240..1080 and returns {w, h, 1}. Its callers include the renderer's set-up 0x7E40A0.
  Nothing else references the globals.
- **0x7E40A0** stores 1920 / 1080 into the renderer's **[+0x28F8] / [+0x28FC]**: the display size. The
  game registers its display buffers at it (2560 x 1440 when patched).
- **The surface slot table 0x18DEA40**: 20 render-target slots of 0x1C bytes (+0x08 format, +0x14 width,
  +0x18 height), read once by 0x81AB80, which packs them into one pool (0x81A8F0 allocates
  0x1C210000 bytes, limit 0x1C200000 at [+0x155DC]). Sizes: 1920x1080 (slots 0-2, 8, 10-13, 19),
  480x1080 (3-4), 480x270 (5-6, 14), 960x540 (7), 2048x2048 (shadows, 9 and 15-18).

`tools/ps4_setup/d1-res-patch.py W H` writes a patch for all three (the 2048 shadow slots kept).

**The 2048 limit.** The boundaries in the broken pictures fall at 2048, 2048 x r and 2048 x r^2 with r =
2048 / width (2560: 2048, 1638, 1310; 2304: 2048, 1820, 1618, all as measured): an image the game
treats as full width is 2048 texels wide, and two passes sample it in normalised coordinates. The
surfaces the game asks for are all the new size (`tools/ps4_setup/d1-surfaces.py` at 2304 x 1296:
classes 1-4 are 2304x1296, 1152x648, 576x324 and 288x162; explicit sizes 640x360, 320x180, 160x90,
40x90, 80x90, 320xH, and the 1536x1536 shadow in slot 9), so the 2048-wide image is made elsewhere.
No 2048 clamp exists in the emulator's video core; the seven `cmp ..., 0x800` + `cmov` in the game are
allocator sizes. Two float constants tied to 1080p exist and are
not the cause: a (1920.0, 1080.0) pair at 0x166EE18 that 0x982310 compares a size with to choose one of
two objects, and 1080.0 at 0x16675B0 that 0x89E941 divides a height by (a UI scale, likely).

## Next

- **No render target is 2048 wide.** The fork's `D1_TRACE_WIDTH=2048` (6bab075; every new image of
  that width, once per address) at 2304 x 1296 (session res-2304-b) listed 487 images, all block-
  compressed content textures (Vulkan formats 133-141, mip-mapped).
- **The passes that stop at 2048** (fork 26fada0, `D1_TRACE_COVER=2048`: viewports or scissors with
  that right edge, dispatches that wide; session res-2304-c), once each:
  - a full-window viewport (clipping off) with the **screen scissor** at 0,0 - 2048,1296;
  - a **viewport 2048 wide**, 1296 high, y flipped, on the 2304 x 1296 target (screen scissor 2304);
  - the same two at 2048 x 960 (another target).
  The height follows the render size and the width stops at 2048: the game derives these from
  min(width, 2048) or from a fixed capacity (for example 128 tile columns of 16 pixels), not from a
  2048 constant: no code reads a 2048.0 float, and the integer `cmp ..., 0x800` + `cmov` sites are a
  text routine and allocator sizes. In memory, per-view structs 0x2900 bytes apart hold (2048, 1296)
  at +0 and (2304, 1296) at +0x18, but they are scratch written by the copy helpers 0x7DFB9F and
  0x7DE416 with many values, so the writer of 2048 is further up.
- **The command words** (fork 0b3eacd: `D1_TRACE_COVER` also logs the guest address of a word that
  sets the screen scissor's right edge to n or viewport 0's x scale to n/2; session res-2304-d): the x
  scale 1024.0 (0x44800000) is written into four command buffers in rotation, 0x80000 apart
  (0x2C3D8xxxx, 0x2C3E0xxxx, 0x2C3E8xxxx, 0x2C3F0xxxx), but the layout differs frame to frame: a write
  watch on one word (0x2C3E0C21C) caught many unrelated values, mostly copied in by code outside the
  game image. Following the value back that way is long.
- Next, cheaper: find the pass by its shaders (the emulator knows the pixel shader of the draw with the
  2048 viewport) and the game code that binds that shader, or look for a fixed capacity (tile columns)
  in the deferred-lighting set-up.
- Up to 2048 x 1152 works now (14% more pixels than 1080p). The sky's banding there is not new: the
  1080p reference at the same spot (session res-1080-ref) has the same.
