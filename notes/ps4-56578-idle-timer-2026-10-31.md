# PS4 56578: where the idle return to orbit gets its 15 minutes (31 October 2026)

The client returns an idle Guardian to orbit with `peer_leave_request` reason `0x4ca36d9a`
(`error.inactivity_timed_out`) 15 minutes after the last button press: 15 minutes in PvE
activities and 60 in social ones, with 60 seconds' grace ([30 October](ps4-56578-tower-stay-vendors-2026-10-30.md)).
This note finds that limit in the executable and tests it with a patch. Addresses are 56578
executable addresses. Owned inputs and run output stay outside the repository.

## The timeouts are named tunables in the client config

The client config's defaults constructor (`0x34E620`) stores five timeouts together:

| Field | Instruction | Default |
|---|---|---|
| `+0x3214` | `0x352583 mov dword [rbx+0x3214], 0xDBBA0` | 900,000 ms (15 min) |
| `+0x3218` | `0x35258D` | 300,000 ms (5 min) |
| `+0x321C` | `0x352597` | 300,000 ms (5 min) |
| `+0x3220` | `0x3525A1` | 3,600,000 ms (60 min) |
| `+0x3224` | `0x3525AB` | 3,900,000 ms (65 min) |

15 and 60 minutes are the PvE and social limits. The three 15-and-5-minute fields are registered as
named tunables in `0x9C2370`. Each 0x40-byte entry holds a 64-bit name hash, a getter and a setter:

| Field | Name hash | Getter | Setter |
|---|---|---|---|
| `+0x3214` | `0xb4ce05778d5207ce` | `0x10C7750` | `0x10C7800` |
| `+0x3218` | `0x86c66749ef7e38b2` | `0x10C7850` | `0x10C7900` |
| `+0x321C` | `0x74dfc81d51a16160` | `0x10C7950` | `0x10C7A00` |

The tunable system (`0x2F60470`) queries the config through `0x9BE3D0`, which is registered at
`0x9BE613`. That function hands out `+0x3210`, `+0x3214`, `+0x3218` or `+0x321C` by the kind it is
asked for (a jump table of five cases at `0x9BE4DC`). So the constructor's default is the value in use
unless something calls a setter.

## The server can set them at sign-on

The defaults constructor runs inside `0x1DB2E0` (called at `0x1DB392` and `0x1DB48F`). That function
resets the engine configuration before the sign-on `client_config.3` delta is applied. The delta's
setter switch (`0x1033F80`) has a case for each of these fields. Every case adds its offset to the
engine-config global `[0x2693DF8]`, as the content-manifest URL's key 100 does, and reads the value
with `read_fixed32` (`0xA2180`):

| Key | Field |
|---|---|
| 1019 | `+0x320C` |
| **1020** | **`+0x3214`, the PvE limit** |
| 1021 | `+0x321C` |
| **1022** | **`+0x3220`, the social limit** |
| 1023 | `+0x3224` |
| 1024 | `+0x3228` |
| `0x60CF7F` (sparse) | `+0x3218` |

The responder now sends keys 1020 and 1022 when `D1_INACTIVITY_MS` and `D1_SOCIAL_INACTIVITY_MS`
are set, and only to build 56578. An unknown key aborts the whole sign-on parse, and these keys have
not been checked against 01.29. No client patch is needed.

## The probe

`ps4/patches/CUSA00219-56578-lab-orbit-idle-probe.xml` is the lab patch plus one line. It sets the
`+0x3214` default to 120,000 ms (2 minutes): the imm32 at `0x352589` becomes `C0 D4 01 00` (original
`A0 BB 0D 00`; patch address `0x752589`). `lab/tower-route/ending-run.ps1 -ClientPatch <file>` passes
a patch through `d1-agr-run.ps1` to `d1-lab-served.ps1`.

## Result

**Run sense78 (the probe patch, the full route).** The emulator logged the probe line as applied
(`Value: C0D40100`). The replay and the fight press buttons often enough that nothing happened for
36 minutes of mission. Then, at the end of the hangar fight, there was a gap: the last press was at
20:35:13, and at 20:37:21 the client sent `peer_leave_request` with reason `0x4ca36d9a`. That is
2 minutes 8 seconds later, where the default gives 15 minutes. So `+0x3214` is the PvE inactivity
limit. The kick cut the run short before the outro.

**Run sense79 (no client patch; `D1_INACTIVITY_MS=120000`).** This was a tutorial boot with the
ordinary lab patch, where the responder sent key 1020 = 120,000 in the sign-on delta. The last press
was at 20:48:11, and the client sent `peer_leave_request` `0x4ca36d9a` at 20:50:09, 1 minute 58
seconds later. So the server sets the limit without patching the client.

## Using it

- `D1_INACTIVITY_MS` (PvE) and `D1_SOCIAL_INACTIVITY_MS` (social) are responder variables in ms, for
  example `ending-run.ps1 -ExtraEnv D1_INACTIVITY_MS=86400000` for a day. Unset, the client keeps
  its own 15 and 60 minutes.
- The value is a u32 of milliseconds, so it goes up to about 49 days. A value that large has not been
  tried: the comparison may be signed, so stay at or below 2,147,483,647.
- The 60 seconds' grace and the "STILL THERE?" prompt are not separate keys found here. `+0x320C`,
  `+0x3218`, `+0x321C`, `+0x3224` and `+0x3228` are unnamed.
- The probe patch stays in `ps4/patches` as the record of the identification. Runs don't need it.
