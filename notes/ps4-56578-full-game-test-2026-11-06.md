# PS4 56578: the first integrated full-game test (6 November 2026)

This is the first native run of everything built on 5–6 November (#304–#333), started with
`tools/ps4_setup/d1-full-game.ps1` and the `ps4/profiles/full-game.env` profile. Each run used
build 56578 on the deployed emulator (0.19.0, fork #6), with the contained lab network. The run
folders are under `D1_STAGING\full-game\`; their logs stay private.

This note records what each run showed, and every fault the test found with its fix on branch
`fix/full-game-boot`. "Played" means the client reported the cinematic's start (incident 2681) and
its end (891).

## The runs

| Run | Setup | Result |
|---|---|---|
| base1 | `baseline.env` (all new subsystems off) | Signed on and reached orbit: the lab, emulator and sign-on are fine. The timed title taps all fired before the title (F1). |
| fg1, fg1b | `full-game.env` | Refused before boot (F3), then the activity host exited on an empty knob (F4). |
| fg1c | `full-game.env` | The responder hung at start (F5); after its fix, every server started with every subsystem on. Signed on to orbit: the store, multiplayer, native RSAT, 530 generated worlds, 24 public lists, the script bridge and the rewards forward all loaded without warnings. |
| fg2 | + tutorial Guardian, `D1_AH_ACTIVITY_REMAP=164:165` | The script bridge ran cine_reveal, but the client never left the initial slice load (F7, F8). |
| fg3b | the bridge off, the step schedule `cine-reveal-steps.txt`, everything else on | **Both reveal cinematics played**, then lifetime 8 sent the client to orbit. The new subsystems do not block the reveal; the bridge did. |
| fg2c | the bridge with the F7/F8 fix | **The first cinematic played from Destiny's own script.** The Tower cinematic's record was held back (F11). |
| fg2d | + F11 | The slice-26 list went out in full; the client's matchmaking was answered by the multiplayer directory. The Tower cinematic did not start (F12). |
| fg2e | + F12 | The same: the Tower play came 5 s after the move to 26 (F13). |
| fg2f | + F13 | The first list went out 0.3 s after the join, at stamp 0, and was never answered (F14). |
| fg2g | + F14 | **The whole reveal played from the scripts**: lifetime 0 → 1 → 4 → 6 → 8, both cinematics, the activity-complete envelope `[965, 2937, 2009, 614]`, the grant and the hand-off forwarded, `cine_reveal ended (Completed)`. The responder refused the grant and the hand-off (F15), so the client went to orbit, not the Tower. |

## The faults

| # | Fault | Fix |
|---|---|---|
| F1 | The contained boot's title taps are timed (60 s, then 3 taps 12 s apart); a boot that compiles shaders reaches the title later. | Also tap while the client's log shows `bootflow:intro_screen_display` (`02fae356`). |
| F2 | (test tooling) A watcher counted the thread name `BLOCK_DETECT` as a crash. | Not a game fault. |
| F3 | After a git checkout, a `Cargo.toml` with a new time but the same content left the launcher calling a fresh binary stale. | When only file times are newer, cargo's clean exit wins (`f613f20d`). |
| F4 | PowerShell 7.6's `Set-Item env:K ''` keeps the variable empty, so every "off" knob reached the servers as `''`. The activity host read `D1_AH_SCRIPTS_SCOREBOARD_COLUMNS` as a path and exited. | Empty values are removed (`02fae356`). |
| F5 | `start_control` wrote the store's state file from inside `global()`'s `OnceLock` initialiser: a re-entrant initialisation that deadlocked the responder with `D1_STORE` and `D1_STORE_CONTROL` on (from #323). | The first state file is written by the control thread (`d0c19635`). |
| F6 | (test design) The geared Guardian lands in orbit; launching needs Director input. | Automated launches use the tutorial Guardian, whose first mission launches by itself. |
| F7 | The bridge started the scripts at the join, while the client was still loading, and its first list lacked the world list's values. | Lifetime 0, the world list merged, a 60 s start cushion, no teleport to the start slice set (`4146d48f`). |
| F8 | The bridge's first lifetime came from `D1_AH_SENSOR_PHASE` (3). That knob also enables the sensor path, so it stays set. | The bridge starts at the list's own phase, else 0 (`4146d48f`). |
| F9 | Windows Firewall asked about the servers on every run: each run copied them to a new folder. | One fixed `D1_STAGING\full-game\bin` (`f613f20d`, `d2773d94`). |
| F10 | A first start (a new store, the new server path) took longer than the boot's 30 s readiness window. | 90 s (`804040cc`). |
| F11 | After the move to slice set 26 the bridge still served slice 25's list, so the Tower cinematic's record `0x2fe7dbe6/0x6/1` was held back. | The list follows the slice set and goes out in full at the move (`fb9bdca0`). |
| F12 | The Tower cinematic's record had no served value, so it went out at the default with no cast. | `D1_AH_SCRIPTS_SLICE_LISTS` gives the step lists' values as the base image (`0c37d8e5`). |
| F13 | The scripts played the Tower cinematic 5 s after the move, before the client had loaded slice set 26. | The script clock holds until arrival plus `D1_AH_SCRIPTS_ARRIVAL_CUSHION` (20 s) (`a50e63e0`). |
| F14 | A first list sent 0.3 s after the join, before the client's world setup, was never answered. | No stamp 0; an unanswered list is re-sent (`D1_AH_SCRIPTS_LIST_RETRY`); the start cushion counts from the first udt 6 (`b769762b`). |
| F15 | The client identity's character field (`+0x18`) holds the profile SOID (`0xd100000000000201`), so the responder found no such player and, under `D1_MP=1`, refused the grant and the hand-off. | A player is named by its character or its profile SOID, with the account still required (`0ab8c345`). |
| F16 | Frames during the Traveler cinematic were black in fg2g. | Not a fault: the cinematic opens on black for about 15–20 s (fg2c, fg2d and fg2e frames after that are bright). |
