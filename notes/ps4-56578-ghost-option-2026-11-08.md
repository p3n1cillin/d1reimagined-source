# PS4 56578: activity options from the server, and the Ghost in the palm (F54) (8 November 2026)

When our Guardian has no weapon equipped, the first-person view shows the Ghost hovering over the
open palm. This happens in A Guardian Rises until the rifle, and in Restoration and The Dark Within
with the tutorial character. The launch footage shows no hands in that stretch. Two read-only
passes over the 56578 executable (Ghidra) traced the client side and the server's way in. The server can now set
activity options (below), but the option they pointed to does **not** remove the palm Ghost
(run gh1).

## How the Ghost gets into the hand

- **Every Ghost spawn passes `0x741af0`.** It refuses when:
  - the unit is not locally owned;
  - the unit's Ghost template (`+0x1210`) is -1. It is copied from the gear blob `+0x324` in
    `0x73fd50`, probably the equipped shell;
  - the **activity option `0xB3C6F690`** is set and true.
- **Into the hand: `0x742820`.** With equipment slot 3 empty, it spawns the Ghost, attaches it to
  slot 3 and sets Ghost state `+0x2a8` = 1. Two callers:
  - the `ghost_deploy` action's start `0x379980`, when the action definition's `+0x1c` flag is set.
    Content decides when this action runs;
  - `ghost_summon`'s update `0x37c050`, only after a touchpad press. Its chain is `+0x1418` ←
    `0x744990` ← the CUI deterministic globals `0x9828d0` ← `0xabab40` ← the touchpad state
    `0xabae10`.
- **The light-volume Ghost: `0x741690`.** It floats in light volumes (state 9). Option
  `0x0150F05D` blocks it. Option `0x0AA3660F` is read in the weapon refresh `0x5a5320`; its meaning
  is unknown.

No code rule turns "no weapon equipped" into the deploy. That rule is most likely the player's
action content. The option looked like the lever, since with `0xB3C6F690` true no Ghost object
should spawn at all. Run gh1 (below) says otherwise.

## Where the option comes from

- **The table.** The lookup `0x118870` reads the activity game system's "Activity Options Game
  State" table (`c_activity_game_system` at `0x26ae458`). Its manager (`singleton+0x18`, slot
  `+0x40` = `0x3d95f0`) returns the table.
- **Its one writer: `0x417b00`, at activity start** (slot 2, `0x417810`). It merges, later entries
  replacing earlier ones:
  - content options: the activity tag's list `+0x128`, conditional option tags, the global tag's
    list, per-slot bools;
  - **the game options list:** count at `+0x12fc`, 50 entries of 24 bytes at `+0x1300`.
- **`0xB3C6F690` can only come from the game options list.** It occurs once in the executable, at
  its store `0x743dc2`, and in no exported activity-options tag. No mission-script built-in sets an
  option.
- **The game options list comes from the server's udt 1 `global_activity_state`** (`0x80800E76`,
  inner `0x80800B8F`). Its blob `+0x60` is `0x80800CC5`, whose `+4` is the list `0x8080533D`: a
  6-bit count at blob `+0x64`, then 50 × 24-byte `0x80800D17` entries at `+0x68`, each a u32 name
  hash and a typed value.
- **It is copied once.** `0x7a9880` copies it at `setup:activity_world_transition` (`0x7a8dd0`;
  "Unable to get world options from the activity client options" if missing). `0x754c20` then
  copies it into game options, and game start `0x906530` copies it into the game globals that
  `0x417b00` reads. **So the option must already be in udt 1 when the client starts the world
  transition into the activity.** Sending it later does nothing until the next activity start.

This also answers the Crucible note's open question
([crucible wire](ps4-56578-crucible-wire-2026-11-06.md)): the manager's table is built from the
global activity state's list, not from the lifetime row.

## Sending options: done

- **The typed values are bound.** The bool is `0x80800004` (a 1-byte struct, one kind-2 field) and
  the int is `0x80800007` (an i32 biased by `0x80000000`). The client's well-known type table
  (`0x1997310`, 300 `{cell, name hash}` rows; cells from `0x28DB450`, filled by `0xEE100`) maps the
  bool cell (hash `0x8ED4248C`) and the int cell (`0x28DBD70`, hash `0xA801403A`) to those
  records. The kind-0x29 encoder `0x102A650` writes the handle as `0x80800046` (a set bit, then 32
  bits), then the payload as that handle's object. A bool entry is 66 bits.
- **The codec knows them.** `d1_oracle::sensor::TYPED_VALUE_TYPES`, and udt 1's oracle is built with
  those types. A bool and an int option round-trip byte-identical through the client's own encoder
  (`a_typed_option_list_round_trips_through_the_clients_codec`, with `D1_EBOOT`).
- **The host sends them.** `GlobalActivityState::set_option` fills the list (count `+0x64`, entries
  `+0x68`). The refusal now covers only untyped entries. `D1_AH_ACTIVITY_OPTIONS=INDEX:HASH=VALUE[,...]`
  (VALUE `true`, `false` or an int) serves them in that activity's `global_activity_state`.

## Run gh1: `0xB3C6F690` is not the palm Ghost

A Guardian Rises with `D1_AH_ACTIVITY_OPTIONS=164:0xb3c6f690=true`, scripted to the rifle:
- **The client took the option.** Its memory holds the entry `{0xB3C6F690, 0x80800004, 1}` in
  several copies, one in a hash-sorted table beside activity 164's own content option
  `0xB3E043B7`.
- **The Ghost still hovers over the palm**, from the spawn into the Wall (frames 17–20).

So the palm pose doesn't go through the spawn gate's option refusal, or the gate isn't the
pose's path. That leaves the `ghost_deploy` action's trigger (content) as the likely source. The
light-volume option `0x0150F05D` and the weapon-refresh option `0x0AA3660F` are untested. Nothing is
served by default.

## Before 8 November

`GlobalActivityState` refused any non-empty list. The codec could not encode the entries' typed
value then: kind `0x29` with no bound tag, the same gap the Crucible's `score_to_win` hit. The
live captures could not settle the value either: the 56578 codec does not decode the 360's udt 1,
and the option hashes appear nowhere byte-aligned in the 56 captures.

## Runs gh2 and gh3: more ruled out

- **gh2, the player bundle's two bools.** The live A Guardian Rises host served the bundle with `+8`
  and `+9` at 0 until the rifle, then 1 (#366, `D1_AH_UNARMED_UNTIL_PHASE=164:3`). Served that way, the
  palm Ghost is unchanged. The rifle still works after the arming.
- **gh3, the other two options.** `0x0AA3660F` (read in the weapon refresh) and `0x0150F05D` (the
  light-volume Ghost), both true: the palm Ghost is unchanged.
- **Retail's own new character.** The live A Guardian Rises capture is a brand-new Warlock: a 501
  create, then 12 items. It had the Generalist Shell equipped and no weapon, the same state as ours,
  and retail shows no palm Ghost.

Still possible: retail's own A Guardian Rises scripts (ours are reconstructions) or client/emulator
behaviour.
